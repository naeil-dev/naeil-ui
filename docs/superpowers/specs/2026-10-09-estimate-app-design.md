# 개인 견적 앱 재설계

상태: 2026-10-09 사용자 검토 승인. 사용자가 문서를 제시받은 뒤 “응 진행해줘”로 이 설계에 따른 구현 계획 작성을 승인했다. 제품 코드·새 저장소·배포 리소스는 아직 생성하지 않았다.

## 1. 목적과 확정 범위

사용자는 견적 조건을 바꾸며 금액과 투입 공수의 변화를 확인하고, 회사별 여러 견적안을 비교하려 한다. 업로드한 `見積シミュレーター.html`은 기능과 계산 규칙을 이해하는 자료다. 기존 화면, 엑셀식 표 배치, 탭 구조를 재현하지 않는다.

대화에서 확정한 사항:

- 기본적으로 혼자 사용하는 독립 웹 앱이며 naeil의 서브도메인에 둔다.
- 우리 디자인 시스템으로 화면과 작업 흐름을 새로 설계한다.
- 엑셀을 사용하거나 엑셀과 연동하지 않는다.
- JEV처럼 비밀번호 하나로 입장한다. 개인별 계정·회원가입·팀 권한은 만들지 않는다.
- DB 없이 서버 JSON 파일, 자동 저장, 자동 백업을 사용한다.
- 여러 탭의 오래된 편집이 새 데이터를 덮어쓰지 않도록 버전을 확인한다.

이 문서의 제안 기본값:

- 원본의 업무 언어·통화를 이어 일본어 UI와 JPY로 시작한다. 번역 가능한 메시지 구조는 유지하되 1차 범위에 언어별 번역 작업을 추가하지 않는다.
- 임시 제품명은 `見積`이다. 최종 제품명과 실제 서브도메인 이름은 배포 준비 때 확정하며, 개발은 설정 가능한 APP_ORIGIN을 사용한다.
- 원본의 회사명·인명·개별 단가는 배포 초기 데이터에 넣지 않는다. 계산 검증용 수치와 익명 fixture로만 사용한다.
- 기본 RR 0.565, 올림 단위 100,000엔, 1인월 160시간, 세율 10%는 편집 가능한 초기 계산 기준이다.

성공 기준: 견적을 생성하고 인력·기간·경비를 조절하는 동안 최종 금액을 확인할 수 있다. 저장 완료된 견적은 다른 기기에서도 로그인 후 열 수 있다. 새 단가 기준이 기존 견적을 조용히 바꾸지 않는다.

## 2. 선택한 접근

| 접근 | 특징 | 판단 |
| --- | --- | --- |
| 브라우저 저장 중심 | 서버 구성이 작지만 기기별 데이터가 분리됨 | 채택하지 않음 |
| 단일 서버 + JSON | 적은 데이터와 1인 편집에 맞고 파일 단위 복구가 쉬움 | 사용자 선택 |
| DB + 사용자별 계정 | 공동 편집·권한·대규모 조회에 유리하지만 현재 요구보다 큼 | 1차 범위 밖 |

공유 UI 저장소는 라이브러리로 유지하고 앱은 독립 소비 프로젝트로 만든다. 현재 작업 디렉터리에 제품 라우트나 업무 로직을 추가하지 않는다. 이 문서는 현재 대화가 시작된 저장소의 설계 기록이며, 구현 계획에서 독립 프로젝트 위치를 명시한다.

## 3. 화면과 작업 흐름

앱 모드는 Operate다. 주된 작업은 견적 편집이며 장식용 대시보드나 소개 페이지를 두지 않는다.

### 입장

`/login`에는 제품명, 비밀번호 입력, 입장 버튼만 둔다. 잘못된 비밀번호·시도 제한·서버 설정 오류를 입력 근처에 표시한다. 로그인 후 견적 목록으로 이동하며, 열려 있던 견적에서 세션이 만료되면 같은 탭의 재로그인 Dialog로 편집 내용을 유지한다.

### 견적 목록

`/estimates`를 기본 화면으로 삼는다. 상단의 새 견적 버튼, 회사 필터와 검색, 최근 수정 순의 목록으로 구성한다. 각 항목에는 회사·견적명·기간·세전 금액·수정 시각을 보여준다. 회사 관리는 목록의 회사 선택 영역과 설정의 관리 Dialog에서 제공한다.

빈 목록에서는 첫 견적 생성이 주된 행동이다. 생성 시 회사와 견적명을 받으며, 새 회사는 같은 흐름에서 추가할 수 있다. 완료하면 편집 화면으로 이동한다. 불필요한 통계 카드나 가상의 매출·수주 상태를 넣지 않는다.

### 견적 편집

`/estimates/[id]`의 상단에는 회사·견적명, 저장 상태, 복제·삭제 행동 메뉴를 둔다. 복제는 원본의 값과 계산 기준을 그대로 복사하고 새 ID를 부여한다.

본문에는 기본 조건, 투입 인력, 경비를 순서대로 배치한다. 넓은 화면에서는 옆에 최종 금액 요약을 sticky로 유지한다. 요약은 세전 금액을 가장 크게, 세금 포함 금액·인건비·경비·총시간·인월을 보조 정보로 표시한다. 부족하거나 잘못된 입력이 있으면 확정 합계처럼 보이는 숫자를 표시하지 않고 수정할 항목을 알려준다.

인력 입력은 긴 스프레드시트를 대체하는 반복 행으로 만든다. 기본 행에는 이름/역할, 직위, 투입률, 인원과 산출 금액을 보여준다. 펼친 행에서 시간/일, 개별 기간, 단가 재정의를 편집한다. 투입률은 사용자가 읽기 쉬운 백분율로 입력한다. 여러 행을 펼쳐 두거나 키보드로 다음 입력으로 이동할 수 있다. 반복 조작마다 Dialog를 열게 하지 않는다.

경비는 항목·단가·수량·인원으로 구성하고 메모는 보조 입력으로 둔다. 명시적 0과 빈 값을 구분하며 수량·인원 기본값은 1이다.

편집 아래의 별도 분석 영역에 계산 명세와 월별 공수를 배치하고, 주별 상세는 기본적으로 접어 둔다. 월별 차트에는 동일 값을 확인할 수 있는 텍스트/표를 함께 제공한다. 이름별 색은 보조 단서이며 범례와 이름을 항상 함께 표시한다.

### 견적 비교

목록에서 같은 회사의 견적안 2~4개를 선택해 `/compare?ids=...`로 이동한다. 비교 기준안을 바꾸면서 세전 금액·공수·기간·인건비·경비의 값과 차이를 볼 수 있다. 비교는 저장된 값으로 계산하며 미저장 편집을 암묵적으로 섞지 않는다. 기본 화면은 간결한 비교표이고 상세는 선택적으로 펼친다.

### 설정

`/settings`에는 기본 계산 기준, 직위별 단가, 휴일, 회사 관리, 데이터 백업/복원을 둔다. 이름·비율·단가를 변경하는 입력은 공유 폼 컴포넌트를 사용한다. 휴일은 날짜와 이름으로 편집하고 명시적으로 관리하는 연도 범위를 표시한다. 범위 밖 견적은 휴일 확인이 필요하다고 알린다. 원본의 제한된 연도 목록을 영구적인 일본 공휴일 데이터로 간주하지 않는다.

휴일은 사용자 관리 방식으로 시작하며 외부 API 연결을 필수로 만들지 않는다. 공휴일 원본 자동 수집은 별도 범위다. 주말 제외는 고정 기본 규칙이다.

원본의 JSON 입출력 목적은 백업/복원으로 유지하되 설정의 보조 행동으로 옮긴다. 새 앱의 버전 있는 형식만 받는다. 이전 HTML 상태 파일의 자동 이관은 1차 범위에 포함하지 않는다. 복원 시 파일 검증, 회사/견적 개수 미리보기, 현재 데이터 백업과 명시적인 교체 확인을 거친다.

## 4. 디자인 시스템과 레이아웃 계약

시각 권위는 루트 `DESIGN.md`, `src/tokens/*.json`, `docs/design/v2-migration.md`다. 사용자 승인인 neutral light/dark, Pretendard와 일본어 Noto Sans JP, 본문·입력 16px, 보조 글자 14px, comfortable/compact 간격, 짧고 절제된 모션을 적용한다.

`@naeil/ui@0.3.0`을 고정하고 `@naeil/ui/ui`의 Button, Input, Select, Tabs, Dialog, DropdownMenu, Textarea, Badge, Toaster를 직접 소비한다. `/theme.css`, `/globals.css`, `/components.css`와 패키지 dist를 대상으로 하는 Tailwind source scan을 설정한다. 폰트는 소비 앱이 직접 제공하고 라이선스 고지를 유지한다. 스타일 복사를 패키지 통합으로 부르지 않는다.

값 선택은 Select, 복제·삭제·백업 같은 행동 선택은 DropdownMenu다. 업무용 반복 행·비교표·차트는 앱 소유다. 공유 패키지에 견적 전용 컴포넌트를 추가하거나 토큰을 바꾸지 않는다. Nav의 사이트 프로젝트 메뉴를 업무 탐색 구조로 강제하지 않고 공유 primitive로 앱 탐색을 구성한다.

| 항목 | 계약 |
| --- | --- |
| 공통 프레임 | 로그인·목록·편집·비교·설정의 제품명과 우측 테마/세션 영역의 기준선을 동일하게 유지한다. 로그인에서는 인증이 필요한 메뉴를 숨기되 프레임 자체를 이동하지 않는다. |
| 앱 탐색 | 고정된 상단 견적/설정 탐색. 회사별 세로 사이드바는 두지 않아 입력·비교 공간을 확보한다. |
| 기본 콘텐츠 폭 | 목록·편집·비교는 공유 list 기본 1,200px cap을 출발점으로 한다. 설정의 폼은 같은 프레임 안에서 640px, 로그인 폼은 480px 이내에 둔다. |
| 편집 열 | 1,200px 안에서 편집 영역을 주로 사용하고 요약은 내용에 필요한 폭만 배정한다. 실제 컨테이너 여유가 없으면 한 열로 전환한다. 숫자와 긴 직위명을 압축해 두 열을 강제하지 않는다. |
| 좁은 화면 | 합계 요약을 기본 조건 위에 두고 간결한 금액/저장 상태 줄을 sticky로 제공한다. 상세 입력은 세로로 펼치며 비교표만 지역 가로 스크롤을 허용한다. sticky 영역은 키보드 포커스와 오류 안내를 가리지 않는다. |
| 비교 조건 | 390/768/1440/2560px, light/dark, 일본어 UI 및 한국어·영어가 섞인 긴 데이터. 빈 목록·많은 견적·긴 이름·로딩·저장 실패에서 같은 조건의 경로를 비교한다. |

공유 터치 영역 44px, 본문 대비 4.5:1, 큰 글자·필수 경계/상태 대비 3:1을 확인한다. 입력 행에서 compact를 선택하더라도 글자 크기를 줄여 밀도를 맞추지 않는다. reduced-motion 설정을 따른다.

현재 시점에서 원본만 데스크톱 브라우저로 확인했다. 새 앱의 위 폭·배치가 실제로 검증됐다는 뜻은 아니다. 레이아웃 수치는 첫 구현을 검사할 출발점이며 필요하면 측정 근거와 함께 제품 수준에서 조정한다.

## 5. 계산 규칙과 데이터 의미

화면·파일 저장과 독립된 순수 계산 모듈을 사용하고 브라우저와 서버가 같은 모듈을 공유한다. 입력 중 미리 계산하며 서버는 클라이언트가 보낸 합계를 신뢰하지 않고 다시 계산한다.

- 영업일은 시작일과 종료일을 포함한 평일에서 설정된 휴일을 제외한다. 날짜는 시간대가 없는 YYYY-MM-DD로 다루고 실제 존재하는 날짜인지 검사한다.
- 인력의 개별 기간이 비어 있으면 견적 기간을 상속한다. 개별 기간이 견적 기간 밖으로 나가면 차이를 표시하며, 원본처럼 해당 개별 기간의 영업일을 계산한다.
- 공수 = 영업일 × 시간/일 × 투입률 × 인원. 인월 = 총공수 ÷ 1인월 시간.
- 인건비 = 표준 시간 단가 × RR × 공수의 합. RR은 할인율이라는 미확인 의미로 바꾸지 않고 적용 배율로 설명한다.
- 원본과 같이 인건비 합을 먼저 엔 단위로 반올림하고 지정 단위로 올림한다. 올림 단위가 0이면 엔 반올림만 한다.
- 경비 = 단가 × 수량 × 인원. 세전 합계 = 올림 처리한 인건비 + 경비 합.
- 세금 포함 합계 = 세전 합계 × (1 + 세율)을 엔 단위로 내림. 인월 단가 = 올림 처리 인건비 ÷ 총인월이며 0인월에서는 해당 없음으로 표시한다.
- 금액·비율·시간 계산에는 decimal 연산을 사용하고 파일에는 정규화한 decimal 문자열을 저장한다. 정수 인원은 별도 정수 필드다. 표시 반올림을 중간 계산값으로 재사용하지 않는다.
- 1인월 시간은 양수, 인원은 0 이상 정수, 금액·시간·배율은 0 이상 유한수, 투입률은 0~100%로 검증한다. 누락된 단가를 0엔으로 간주하지 않는다.
- 미완성 견적은 누락 필드를 null로 저장할 수 있으나 계산 미완료 상태를 표시한다. 불가능한 날짜·역전 기간·음수·NaN·Infinity는 오류다. 오류 입력은 화면에 유지하고 마지막 정상 서버 저장을 덮지 않는다.
- 기간·행 개수·문자열 길이·요청 크기에 유한한 한도를 둔다. 1차 기본은 견적당 인력 100행, 경비 100행, 기간 10년 이하, 상태 파일/요청 5MiB 이하이며 한도 도달 시 명확히 안내한다.

기존 HTML을 실행해 확인한 fixture는 인력별 45.6/228/570시간, 총843.6시간, 5.2725인월, 올림 후 인건비17,500,000엔, 경비1,500,000엔, 세전19,000,000엔, 세금 포함20,900,000엔이다. 원본 엑셀과 대조한 결과는 아니다.

### 계산 기준 보관 — 새 동작 제안

직위는 이름 대신 안정적인 ID로 연결한다. 이름을 바꿔도 관계가 끊기지 않는다. 직위 삭제는 신규 선택에서 제외하는 보관 처리이며 기존 견적의 표기는 유지한다.

새 견적은 당시 단가·기본 RR·세율·올림 단위·인월 시간·휴일을 자체 계산 기준으로 복사한다. 기존 견적은 설정 변경 후에도 같은 금액을 유지한다. 최신 기준이 필요하면 해당 견적에서 갱신할 항목과 예상 금액 차이를 확인하고 적용한다. 복제한 견적도 원래 기준을 보존한다. 원본의 전역 마스터 즉시 반영 동작과 다른 의도적인 제안이다.

## 6. JSON 저장과 복구

Next.js/React와 단일 Node 서버로 운영한다. 배포 묶음 밖의 지속 데이터 폴더에 `estimates.json`, 이전 사본 디렉터리, 인증 설정을 둔다. 런타임을 Node 24 LTS의 검증한 패치 버전으로 고정하고 pnpm lockfile로 의존성을 고정한다. 일시적인 서버리스 파일시스템이나 복수 인스턴스에 배포하지 않는다.

상태 문서는 `schemaVersion`, `revision`, `updatedAt`, `settings`, `companies`, `estimates`로 구성한다. 회사·견적·행·직위에 안정적인 ID를 부여한다. 계산 기준은 견적 안에 보관하고 파생 합계는 저장의 권위로 사용하지 않는다. 탐색 중인 탭·선택 회사는 업무 데이터와 분리한다.

저장 흐름:

1. 사용자가 입력하면 화면 계산을 즉시 갱신하고 저장 대기로 표시한다.
2. 유효 입력이 600ms 동안 안정되면 변경 내용과 마지막 서버 revision을 보낸다. 미완성 null은 허용하지만 오류 값은 저장하지 않는다.
3. 서버는 세션·Origin·요청 크기·스키마를 검사한다. 쓰기 큐 안에서 revision을 다시 확인한다.
4. 이전 유효 사본을 백업하고 같은 파일시스템의 임시 파일에 전체 문서를 쓴다. flush 후 atomic rename하고 지원 플랫폼에서 디렉터리까지 sync한다.
5. 성공 응답의 revision을 받은 후에만 저장 완료로 표시한다. 요청 중 발생한 후속 입력은 버리지 않고 다음 저장으로 이어간다.

서버 프로세스는 데이터 폴더를 단독으로 사용하도록 시작 시 잠금을 획득한다. 두 프로세스가 같은 파일을 쓰도록 허용하지 않는다. 비정상 종료 뒤 남은 잠금은 기존 프로세스가 없는 것을 확인한 운영 복구 절차로 해제한다.

revision 불일치는 409로 반환한다. 화면은 내 편집을 보존하고 최신 서버 데이터를 불러올 수 있게 한다. 내 버전을 복구 파일로 내려받는 선택을 제공하며 무조건 덮어쓰기나 자동 병합은 하지 않는다.

백업은 정상 교체 직전의 최근 20개 사본을 유지한다. 복원도 새로운 revision을 발급하는 같은 쓰기 경로를 사용한다. 파일이 손상됐으면 빈 데이터로 초기화하지 않고 읽기/저장을 중단해 백업 복구를 안내한다. 최초 파일 없음은 별도 최초 설정 명령으로만 빈 상태를 생성한다. 운영 실행은 유실을 새 설치로 오인하지 않는다.

연결·디스크 오류에는 실패와 재시도 상태를 표시한다. 앱 내 이동은 대기 중 저장을 처리하고 실패하면 편집 화면을 유지한다. 탭 종료에는 미저장 경고를 둔다. DB 대용으로 브라우저 localStorage에 견적 전체를 중복 저장하지 않는다. 저장 완료 전 강제 종료한 입력까지 복구된다고 보장하지 않는다.

로그아웃 전에 저장을 처리하고 실패하면 내보내기/머무르기를 제공한다. 서버에 저장된 데이터를 다른 기기에서 읽는 경로는 동일 인증 API다.

## 7. 비밀번호 인증

JEV의 비밀번호 한 칸 UX와 host-only 세션 경계를 따른다. JEV의 SQLite 세션 저장은 도입하지 않는다. JEV 운영 비밀번호·쿠키·서명 키·DB도 공유하지 않는다.

- 비밀번호 설정은 서버의 숨김 입력 명령으로 수행한다. salted scrypt 해시를 권한0600의 별도 파일에 저장한다. 운영 값을 채팅·CLI 인자·브라우저 저장소·프론트엔드 번들에 넣지 않는다.
- 별도의 서버 signing key로 서명한 최소 세션 payload에 버전과 발급/만료 시간을 담는다. 알고리즘은 서버가 고정하고 안전한 비교를 사용한다. 암호화한 데이터 저장 용도로 쿠키를 사용하지 않는다.
- 유효기간은 24시간. production 쿠키는 `__Host-estimate_session`, Secure, HttpOnly, SameSite=Lax, Path=/이며 Domain 속성을 두지 않는다.
- 모든 업무 페이지와 읽기/쓰기 API가 서명·만료·현재 인증 버전을 검증한다. 인증 설정이 없거나 잘못되면 닫힌 상태로 시작한다.
- 비밀번호 변경은 인증 버전도 바꾸어 기존 쿠키를 모두 무효화한다. stateless 방식이므로 로그아웃은 현재 브라우저 쿠키를 지우며 개별 탈취 토큰의 서버측 폐기 목록은 제공하지 않는다.
- 로그인은 서버 메모리의 요청 제한과 동시 scrypt 검증 제한을 둔다. 단일 프로세스 기준이며 재시작 시 시도 집계는 초기화된다.
- 로그인·로그아웃·업무 변경 요청은 same-origin을 검증한다. 인증 문서/API에는 no-store를 적용하고 비밀번호·세션 원문을 로그에 남기지 않는다.

## 8. 구현 경계

- `domain`: 타입, 스키마, decimal 계산, 영업일, 비교, 계산 기준 복사/갱신.
- `server/storage`: JSON 읽기·검증·쓰기 큐·revision·백업·복원·단독 실행 잠금.
- `server/auth`: 비밀번호 해시 검증·서명 쿠키·인증 버전·요청 제한.
- `app/api`: 인증 경계와 입력 검증, 도메인/저장 모듈 호출. 클라이언트가 임의 파일 경로를 전달하지 못하게 한다.
- `features`: 견적 목록·편집·비교·설정·저장 상태. 폼 상태와 저장 요청을 구분하고 컴포넌트에 파일 처리를 넣지 않는다.

공동 편집·회원 관리·수주 관리·PDF 견적서·Excel·AI 기능·메일 전송·외부 공휴일 API는 1차 범위 밖이다. JSON 백업은 개인 데이터 이동과 복구 목적이다.

## 9. 검증과 출시 기준

구현 계획에서는 다음을 자동/브라우저/운영 검증으로 나눠 실행한다.

- 계산: 익명화한 원본 fixture, 반올림 경계, 윤년·주말·휴일·중복 휴일, 개별 기간, 0공수·0배율, 빈 단가, 잘못된 날짜, decimal 합계.
- 저장: 디스크 실패·중단된 임시 파일·동시 저장·revision 충돌·복원·손상 파일·최초 설정·중복 프로세스·재시작 지속성. 실패했는데 저장 완료로 표시하지 않는지 확인한다.
- 인증: 정상/실패·시도 제한·서명 변조·만료·비밀번호 변경·로그아웃·미인증 직접 API·교차 Origin·설정 누락.
- 흐름: 첫 회사/견적 생성, 인력과 경비 편집, 복제, 비교, 기준 갱신, 삭제 확인, 백업/복원, 재로그인 후 미저장 편집 유지.
- 디자인: 실제 공유 컴포넌트와 폰트, 위 viewport/light/dark 조건, 대비·오류 연결·키보드·포커스 복귀·44px 터치 영역·긴 데이터·페이지 및 표 내부 넘침·reduced motion.
- 공유 패키지는 public export로 실제 빌드 소비한다. 패키지 동작을 바꿔야 하면 별도 범위로 만들고 관련 테스트·Storybook 실제 결과·contrast·packed consumption을 검증한다.
- 출시: 고정 런타임, 지속 데이터 디렉터리, 프로세스 재시작, 인증된 HTTPS, 실제 origin 전용 쿠키와 미인증 차단, 백업 복구를 확인한다. UI 구현 완료와 도메인 연결 완료를 구분해 보고한다.

기존 확인 사항은 아직 해결된 것으로 처리하지 않는다: 원본의 직위명 변경 시0단가, 1인월0시간 시Infinity, 저장 오류 처리 부족, 원본 휴일 범위의 제한, 모바일/새 UI의 미검증. 각 항목은 새 구현의 검사 증거가 생긴 뒤 닫는다.

## 10. 참고와 현재 증거

- 원본 업로드를 읽고 Aside로 1440×900 데스크톱 화면을 확인했다. 원본의 390px 확인은 Aside REPL에서 viewport API가 지원되지 않아 완료하지 못했다.
- 원본 JS의 계산 함수와 내장 assertion을 Node에서 실행했다. 원본 Excel은 받거나 실행하지 않았다.
- `@naeil/ui`의 package exports, 13개 UI family, Nav API, DESIGN.md와 소비 가이드를 읽었다. 새 앱에 패키지를 통합하거나 Storybook을 실행한 단계는 아니다.
- JEV의 로컬 실제 앱 `src/server/auth.ts`, `src/server/session.ts`, README와 STATUS를 읽어 비밀번호 입장·24시간 host-only 쿠키·SQLite 세션을 확인했다. 운영 credential과 DB는 읽지 않았다. 현재 로컬 소스와 공개 운영본의 동일성을 주장하지 않는다.
- Impeccable SKILL/context와 관련 안내를 참고했다. 독립 critique·detector·polish·distill·finish review는 실행하지 않았다.
