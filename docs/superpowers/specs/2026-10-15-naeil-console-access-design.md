# Naeil Console — 도메인별 접근 관리 기능 설계

작성일: 2026-10-15

상태: 사용자 검토용 기능 설계. 구현·배포 완료를 의미하지 않는다.

실제 구성 확인 결과를 반영했다. 근거와 검증 한계는 [2026-10-15 확인 보고서](2026-10-15-naeil-console-access-review.md)를 따른다.

## 1. 목적과 합의된 범위

Naeil Home의 AI 옆에 `Console` 메뉴를 두고, naeil 서비스에 누가 접근할 수 있는지 관리한다. 관리 화면은 기존 Tailscale 내부 Home에서 사용한다. Supabase 대시보드에 들어가지 않고 일상적인 회원·초대·권한 관리를 할 수 있어야 한다.

첫 대상은 `jev.naeil.dev`와 `abestimate.naeil.dev`다. 같은 회원에게 JEV만 허용하거나 두 서비스 모두 허용할 수 있다. 권한 단위는 서비스 도메인이며 서비스 내부 기능별 권한은 첫 버전에서 제외한다. 계정은 공통 사용자 식별자를 사용하는 방향으로 통합한다. 한 번 로그인하면 모든 도메인에서 자동 로그인되는 SSO 동작은 각 앱의 현재 인증 구조를 확인한 뒤 별도로 검증해야 한다.

사용자가 선택한 방향:

- Console 내부에 추가 탭이나 사이드바를 만들지 않는다.
- 회원 목록 중심의 한 페이지와 회원 상세 패널을 사용한다.
- 공개 가입을 막고 관리자가 허용한 사람만 이용하게 한다.
- 도메인별 접근을 독립적으로 관리한다.
- AB Estimate에 허용된 회원은 모두 같은 견적을 보는 공용 작업 공간을 사용한다. 사용자별 데이터 분리는 제외한다. (2026-10-15 사용자 확인)

이 문서가 제안하는 첫 버전 기본값:

- 최초 관리자는 Jay 한 명으로 시작한다. 초기 계정 연결은 검증된 사용자 ID로 수행한다.
- 신규 회원·신규 서비스는 접근 권한이 없는 상태로 시작한다.
- 초대 유효기간은 7일이다.
- 위 7일은 앱의 초대 수락 가능 기간이다. Supabase 인증 링크의 만료와 별개이며, 인증 링크의 실제 유효기간·갱신 방식은 검증 후 UI에 반영한다.
- 첫 버전에서 도메인 등록은 운영 설정으로 하고, 화면에서는 등록된 서비스의 회원 권한을 관리한다.

## 2. 첫 버전에 넣을 기능

| 기능 | 사용자가 할 수 있는 일 | 동작 기준 |
| --- | --- | --- |
| 회원 목록·검색 | 이름·이메일·상태·허용된 서비스 확인, 이름/이메일 검색 | 연결된 공통 인증 계정 조회 |
| 도메인 필터 | JEV 또는 AB Estimate 접근이 허용된 회원만 보기 | 전체 차단 여부를 함께 표시 |
| 회원 상세 | 로그인 방법, 가입일, 전체 상태, 도메인별 권한 확인 | 도메인별 로그인 이력은 수집 전 표시하지 않음 |
| 권한 변경 | JEV/AB Estimate 각각 허용·회수 | 스위치는 편집 상태, 저장 버튼으로 일괄 반영 |
| 회원 전체 차단·해제 | 모든 관리 대상 서비스 접근 차단·복구 | 전체 차단이 개별 허용보다 우선 |
| 회원 초대 | 이메일과 허용할 도메인을 선택해 초대 | 하나 이상의 도메인 선택 필요 |
| 대기 초대 관리 | 초대 대상·서비스·상태·만료일 확인, 재발송·취소 | 수락 전에는 서비스 접근 불가 |
| 관리 기록 | 초대·취소·권한 변경·전체 차단의 실행자와 결과 확인 | 최근 10건, 같은 영역의 ‘더 보기’로 이전 기록 조회 |
| 접근 정책 표시 | ‘초대받은 회원만 이용’ 상태와 관리 대상 확인 | 실제 적용 상태가 확인된 경우에만 적용 완료 표시 |

AB Estimate는 현재 공용 JSON 작업 공간이며 사용자가 이 공유 방식을 유지하기로 했다. 도메인 접근 허용은 같은 견적의 조회·수정·다운로드·복원 기능을 허용하는 의미다. 첫 버전에는 개인별 견적 분리나 읽기 전용 역할이 없다. 초대와 권한 저장 화면에서 ‘허용된 회원은 같은 견적과 설정을 공유합니다’라고 설명한다. 기존 견적·설정·백업을 보존하며, 여러 사용자의 동시 저장에는 기존 revision 충돌 검사를 유지한다. 이 결정 자체가 특정 회원에게 실제 권한을 부여하는 작업은 아니다.

단순한 운영 기능부터 제공한다. 회원 영구 삭제, 역할/그룹, 일괄 권한 변경, 기능별 권한, 결제/구독, 권한 신청·승인함, 관리자 임명 UI, 도메인/DNS 자동 생성은 제외한다. 가입 정책은 첫 버전에서 초대 전용으로 고정하며 공개 가입을 여는 스위치는 제공하지 않는다.

## 3. 화면 구성

상단에는 기존 Naeil Home 프레임과 AI / Console 메뉴를 유지한다. 본문 제목은 `naeil.dev 관리`다. 기능을 설명하는 보조 문구는 ‘서비스별로 접근할 수 있는 사람을 관리합니다’로 한다.

본문 순서:

1. 초대 전용 정책과 관리 대상 도메인. 연결 상태는 `연결 확인 전`, `권한 적용 중`, `확인 실패`로 구분한다. 단순 등록만으로 정상 또는 접근 보호 완료를 표시하지 않는다.
2. 회원 검색, 도메인 필터, 회원 초대 버튼.
3. 회원 목록: 이름/이메일, 허용된 서비스, 전체 상태, 상세 버튼.
4. 대기 중인 초대와 최근 관리 기록.

회원 상세 패널:

```text
회원 상세                         닫기
이름 / 이메일 / 로그인 방법

서비스 접근
JEV          jev.naeil.dev          [허용]
AB Estimate  abestimate.naeil.dev   [차단]

                          취소  변경 저장

회원 전체 차단
모든 관리 대상 서비스의 접근을 중단합니다.
```

`변경 저장`은 변경이 있을 때만 활성화된다. 저장 중에는 중복 제출을 막고, 성공 응답 이후 실제 권한 표시를 갱신한다. 실패하면 편집 내용과 재시도 방법을 유지한다. 저장하지 않고 패널을 닫을 때는 변경 폐기 여부를 확인한다.

전체 차단은 별도 확인 창에서 영향 범위를 알린다. 전체 차단 상태에서는 도메인 허용 설정을 보존하되 편집을 잠근다. 해제 시 이전 도메인 권한이 복구된다는 설명과 대상 목록을 확인 창에 표시한다. Console 관리자인 본인 계정의 전체 차단은 UI와 서버 모두 거부한다.

초대 창은 이메일 입력과 두 도메인 선택만 제공한다. 기본 선택은 없음이다. 기존 회원이면 중복 초대 대신 해당 회원 상세로 안내하고, 대기 초대가 있으면 기존 초대로 안내한다. 대기 초대의 도메인을 변경하려면 취소 후 다시 초대한다. 재발송은 기존 선택을 유지한다.

기존 목업의 정상 상태·예시 회원·로그인 시각은 샘플이다. 운영 화면에서 측정하지 않은 상태나 시각을 채워 넣지 않는다. 디자인은 저장소 DESIGN.md의 중립 색상·Pretendard·콘텐츠 폭과 기존 Home 프레임을 따른다.

## 4. 접근 권한 규칙

서버에서 확인한 로그인 사용자에 대해 다음 조건을 모두 만족해야 접근을 허용한다.

```text
유효한 인증 사용자
  AND 활성 회원
  AND 활성 서비스
  AND 해당 사용자·서비스의 명시적 허용
```

- 등록되지 않은 사용자나 권한 행이 없는 조합은 거부한다.
- JEV의 허용이 AB Estimate의 허용을 뜻하지 않는다.
- 신규 서비스 추가 시 기존 회원에게 자동 허용하지 않는다.
- Console 관리자 권한은 서비스 이용 권한과 별개다. 관리자도 서비스 이용 권한은 명시적으로 부여한다.
- 권한 저장이 완료된 뒤 시작되는 보호 요청은 최신 권한으로 검사한다. 첫 버전은 장기 권한 캐시나 로그인 시점의 권한만으로 판단하지 않는다.
- 권한 회수는 이미 내려받은 파일·데이터를 회수하지 않는다. 실행 중인 요청을 소급 취소하는 기능도 포함하지 않는다. 스트리밍·장기 작업이 있다면 서비스 연결 시 재검사 지점을 정해야 한다.
- 계정 차단은 모든 관리 대상 서비스의 보호 기능을 막는 의미다. 별도의 공개 소개 페이지까지 비공개로 바꾸지는 않는다.
- 사용자 입력 이메일이나 클라이언트가 전달한 사용자 ID를 권한 판단의 근거로 신뢰하지 않는다. 검증한 세션의 고정 사용자 ID를 사용한다.

상태별 사용자 경험:

| 상태 | 웹 페이지 | API |
| --- | --- | --- |
| 미로그인/세션 만료 | 로그인으로 안내, 허용된 복귀 경로 보존 | 401 |
| 로그인했으나 도메인 권한 없음 | 서비스 접근 권한 없음, 계정 전환 안내 | 403 |
| 회원 전체 차단 | 이용이 중단된 계정 안내 | 403 |
| 권한 조회 장애 | 잠시 후 재시도 안내, 보호 데이터 미제공 | 503 |

로그인 페이지, OAuth 콜백, 초대 수락, 접근 거부 안내는 앱 진입 차단에 함께 막히지 않도록 분리한다. 비공개 데이터는 안내 페이지에 포함하지 않는다.

## 5. 초대와 가입

운영 정책은 ‘관리자가 초대한 계정만 이용’이다. 회원가입 버튼을 숨기는 것만으로 이 정책이 구현된 것으로 보지 않는다.

권장 흐름:

1. 관리자가 이메일과 허용 도메인을 선택한다.
2. 서버가 대기 초대를 기록하고 Supabase 관리자 초대 경로로 계정을 준비해 이메일을 보낸다. 이때는 서비스 권한을 활성화하지 않는다.
3. 수신자가 만료되지 않은 일회용 초대를 열고 이메일 소유를 검증한다.
4. 서버가 초대에 연결된 인증 사용자 ID, 수락 상태, 만료와 취소 여부를 검증한다.
5. 초대 수락과 선택한 서비스 권한 부여를 하나의 DB 트랜잭션으로 처리한다.
6. 허용된 서비스로 이동한다. 두 서비스가 있으면 선택 화면을 제공한다.

초대로 준비된 인증 계정은 수락 전에는 대기 초대 영역에 표시한다. 서비스 이용 회원으로 활성화하거나 회원 목록의 활성 인원에 포함하지 않는다. 초대 수락 트랜잭션에서 회원을 활성화한다.

공개 계정 생성을 비활성화하면서 관리자 초대는 허용하는 방식을 우선 검증한다. 현재 Google/GitHub 로그인과 초대 계정 연결이 이 설정에서 실제로 동작하는지 구현 전 확인해야 한다. 일반 OAuth 로그인만으로 초대를 자동 수락하거나 권한을 주지 않는다. 공급자 이메일이 없거나 초대 계정과 일치하지 않으면 자동 연결하지 않는다. 동일 이메일 계정의 연결 동작을 임의로 가정하지 않는다.

메일 발송은 DB 트랜잭션과 분리되므로 `발송 중`, `발송 실패`, `수락 대기`, `수락`, `취소`, `만료` 상태를 구분한다. API 응답이 불명확하면 중복 계정 생성이나 중복 초대를 하지 않고 공급자 상태를 확인한다. UI는 메일 제공자가 요청을 수락한 상태를 실제 수신함 도착으로 표현하지 않는다.

재발송은 앱 초대의 새 버전과 새 유효기간 7일을 사용하고 이전 버전으로 권한을 부여하지 않는다. Supabase 인증 링크의 수명·재발송 API 동작과는 구분한다. 이전 인증 링크가 세션을 만들더라도 취소/교체된 앱 초대로 서비스 권한을 얻을 수 없어야 한다. 수락·취소는 한 번만 성공할 수 있게 처리한다. 취소된 초대의 인증 계정이 남더라도 서비스 권한은 부여되지 않는다. 초대 재시도는 동일 작업 식별자를 사용해 중복 실행을 방지한다. 관리자 초대/재발송 API에는 발송 빈도 제한을 둔다.

현재 프로젝트는 기본 내장 메일을 사용하고 있어 외부 회원 초대 전에 custom SMTP 설정과 발신자 검증이 필요하다. 기존 naeil OAuth 콜백은 code 교환만 처리하므로 이메일 초대 토큰을 검증하는 별도 수락 흐름을 구현해야 한다.

## 6. 구성 요소와 책임

선택지는 서비스마다 별도 회원 목록 운영, 중앙 권한 저장소와 각 앱 검사, 공통 접근 게이트웨이다. 중앙 저장소와 각 앱 검사를 권장한다. 계정을 중복 관리하지 않으면서 API와 데이터 접근까지 같은 권한을 적용할 수 있다. 게이트웨이만 보호하면 앱의 별도 API나 데이터 경로가 남을 수 있다.

권장 구성:

```text
Tailscale 내부 Naeil Home / Console
                ↓ 인증된 관리자 요청
          Home의 관리 서버
                ↓
     Supabase Auth + 중앙 권한 DB
                ↑
    JEV 서버              AB Estimate 서버
    세션 검증 + 자기 서비스의 권한 검사
```

- Console: 회원·초대·권한의 관리 UI. 일반 회원에게 노출하지 않는다.
- 관리 서버: 관리자 인증·인가, 초대 발송, 권한 변경, 관리 기록을 담당한다. 관리자용 Supabase 비밀 키는 서버에만 둔다.
- Supabase Auth: 사용자 식별과 인증을 담당한다. 인증 성공 자체가 서비스 허용은 아니다.
- 중앙 권한 DB: 사용자 상태, 서비스 목록, 허용 관계, 초대, 기록의 기준이다.
- 각 앱: 페이지뿐 아니라 API·다운로드·데이터 조회에도 동일한 권한 검사를 적용한다. DB/Storage 직접 접근이 있다면 RLS/정책도 함께 적용한다.

Tailscale에 연결되었다는 사실만으로 Console 관리자 권한을 주지 않는다. Home의 검증된 서버 세션과 등록된 관리자 식별자를 연결하고 모든 관리 API에서 검사한다. `*.ts.net`의 Home 인증에 `.naeil.dev` 쿠키가 전달된다고 가정하지 않는다. 상태 변경 API는 요청 출처와 CSRF 방어를 갖춘다. 인증되지 않은 클라이언트가 임의 프록시 헤더로 관리자가 될 수 없어야 한다.

실제 Home은 개인 actor가 없는 공용 비밀번호 세션을 사용한다. 이를 Jay 개인 계정으로 간주하지 않는다. 기존 Home 인증을 유지하면서 Console에는 별도의 서버 검증 가능한 Supabase 관리자 세션과 사용자 ID 허용목록을 추가하는 방안을 권장한다. Home 전용 콜백과 host-only 세션을 사용하며 세부 연결은 운영 배포 원본 확인과 인증 흐름 검증을 거쳐 확정한다.

도메인은 사용자가 보는 관리 단위이고, 내부에서는 고정 서비스 ID `jev`, `abestimate`를 사용한다. 각 앱은 서버 설정의 서비스 ID로 자기 권한을 검사한다. 임의 Host나 쿼리 파라미터로 다른 서비스 ID를 고를 수 없게 한다. 등록된 정확한 호스트·콜백·복귀 주소만 허용한다.

## 7. 최소 데이터 모델과 일관성

| 데이터 | 주요 내용 |
| --- | --- |
| 회원 상태 | 인증 사용자 ID, 가입 대기/활성/차단, 변경 시각 |
| 관리자 | 검증된 Home 사용자 식별자와 관리자 상태, 필요 시 연결된 공통 인증 사용자 ID |
| 서비스 | 고정 ID, 표시 이름, 정확한 도메인, 활성 여부, 연결 검증 상태 |
| 서비스 허용 | 사용자 ID + 서비스 ID의 고유한 조합, 부여자, 부여 시각 |
| 초대 | 이메일, 대상 서비스 집합, 연결된 인증 사용자 ID, 상태, 만료, 발송 결과, 초대자 |
| 관리 기록 | 실행자, 대상, 동작, 변경 전/후, 결과, 서버 시각, 작업 식별자 |

초대 토큰 원문이나 로그인 토큰은 기록에 남기지 않는다. 권한 변경과 해당 성공 기록은 같은 DB 트랜잭션에서 저장한다. 실패한 외부 발송은 별도 실패 기록으로 보존한다. 일반 사용자는 권한·초대·관리자 목록을 변경하거나 다른 회원 정보를 조회할 수 없다.

패널 저장은 읽었던 버전을 함께 보내 동시 수정 충돌을 감지한다. 충돌하면 덮어쓰지 않고 최신 상태를 다시 확인하도록 안내한다. 도메인별 권한 변경은 한 번의 저장에서 전부 성공하거나 전부 실패한다.

## 8. 현재 확인된 기반과 구현 전 확인 사항

이 설계 작성 시 이 저장소의 `docs/spec-auth.md`, `docs/tasks-auth.md`, 인증 파일 위치와 쿠키 처리 코드를 읽었다. 기존 인증 문서는 스스로 과거 기록임을 명시하며, 공개 가입과 로그인 사용자 전체의 리포트 열람을 설명한다. 이를 현재 운영 상태나 새 권한 정책의 구현 증거로 사용하지 않는다.

현재 HTML 목업은 독립 샘플이며 Supabase나 실제 Home에 연결되지 않았다. 후속 읽기 전용 점검에서 두 앱이 자체 비밀번호 인증임을 확인했고, AB Estimate의 공용 저장소, Home의 개인 식별자 부재, Supabase 공개 가입 활성·기본 메일 사용·콜백 등록 현황을 확인했다. 운영과 작업 소스가 다르므로 [확인 보고서](2026-10-15-naeil-console-access-review.md)의 배포 식별 근거를 따른다. 다음 표는 구현 전 충족해야 하는 연결 조건이며 아직 E2E 통과를 의미하지 않는다.

| 확인 대상 | 필요한 결과 |
| --- | --- |
| JEV / AB Estimate 저장소·배포 경로 | 보호 페이지·API·파일·직접 DB 접근 경로 목록 |
| 각 서비스의 인증 | 공통 Supabase 사용자 ID를 사용 가능한지, 기존 회원 데이터 연결 방법 |
| Home의 실제 배포 브랜치와 인증 | 현재 UI를 유지할 작업 위치와 서버에서 검증 가능한 관리자 ID |
| 초대와 Google/GitHub 연결 | 공개 생성 차단 상태에서 초대 수락과 이후 로그인 성공, 비초대 가입 거부 |
| 세션·쿠키 | 루트/서브도메인 쿠키 충돌 및 속성 손실 해결, 로그아웃·갱신 검증 |
| 메일 | 승인된 발신 설정, 발송 실패/재발송, 만료·취소 링크 검증 |

이 연결 조건을 충족하지 못하면 적용 완료로 표시하지 않고 해당 흐름의 설계를 수정한다. 권한을 검사하지 않는 앱에 대해 Console만 먼저 만들어 보호가 작동한다고 보고하지 않는다.

## 9. 기존 계정 전환과 적용 순서

기존 계정은 삭제하지 않는다. 초기 관리자 ID와 기존 회원별 JEV/AB Estimate 허용표를 먼저 확정해 명시적으로 등록한다. 기존 로그인 사용자 전체를 자동 허용하는 규칙은 추가하지 않는다.

JEV·AB Estimate의 현재 비밀번호 세션에는 개인 사용자 ID가 없다. 비밀번호를 알고 있던 사람을 특정 계정에 자동 연결하지 않는다. 공통 계정으로 새로 로그인하도록 전환하고, 기존 비밀번호/세션만으로 새 권한 검사를 우회하는 경로를 제거한다. 견적 원본과 백업은 보존한다. 현재 작업 브랜치의 미배포 기능을 인증 변경에 함께 배포하지 않는다.

권장 순서는 중앙 권한 저장소·관리자 연결 → Console 회원/권한 관리 → JEV 연결 검증 → AB Estimate 연결 검증 → 초대/공개 가입 정책의 전체 검증과 운영 적용이다. 실제 전환 전 각 앱의 검사 경로와 초기 허용 데이터가 함께 준비돼야 한다. 공개 가입 차단은 초대 수락 경로 검증과 맞춰 적용한다. 연결 확인 전 도메인은 초대/권한 편집 대상에서 비활성화한다.

장애 시 이전의 ‘로그인만 하면 허용’ 정책으로 자동 복귀하지 않는다. 설정·마이그레이션을 백업하고, 권한 데이터를 보존한 상태로 서비스별 배포를 복구할 수 있게 한다. 운영 배포 작업과 실제 계정 변경은 이 기능 설계 문서 작성 범위에 포함하지 않는다.

## 10. 완료 판단 기준

1. 관리자만 Tailscale Home의 Console과 관리 API를 사용할 수 있다.
2. JEV만 허용된 회원은 JEV를 이용하고 AB Estimate의 페이지·직접 API·데이터 접근은 거부된다.
3. 두 서비스 허용, 모두 미허용, 비로그인, 만료 세션을 각각 구분해 처리한다.
4. 저장 완료 후 새 요청부터 권한 회수가 적용된다. 기존 브라우저 세션만으로 우회하지 못한다.
5. 전체 차단이 두 서비스에 적용되고, 해제 시 확인한 기존 허용 목록이 복구된다.
6. 공개 신규 가입은 거부되고 유효한 초대 수락만 계정 이용과 선택 서비스 권한으로 이어진다.
7. 만료·취소·재사용·이전 재발송 링크, 다른 계정의 초대 수락으로 권한을 얻을 수 없다.
8. 비초대 OAuth 가입, 초대 계정의 OAuth 로그인, 공급자 이메일 누락/불일치를 각각 검증한다.
9. 권한 조회 장애에서 보호 데이터가 노출되지 않는다. API 주소 직접 호출과 클라이언트 입력 변조도 거부된다.
10. 중복 저장·초대·동시 수정에서 중복 계정이나 일부만 적용된 권한이 생기지 않는다. 성공한 변경에는 관리 기록이 남는다.
11. 새 서비스를 등록해도 기존 회원 권한이 자동 생성되지 않는다.
12. 모바일/데스크톱, 양 테마, 키보드 조작, 오류·빈 목록·저장 중 상태를 실제 화면에서 확인한다.
13. 서로 다른 두 허용 계정이 같은 AB Estimate 견적·설정을 조회하고, 한 계정의 저장이 다른 계정의 재조회에 반영된다. 동일 revision에서 충돌하는 두 저장은 하나만 성공하며 나머지는 충돌로 안내한다. 접근 불가 계정에는 공용 데이터가 노출되지 않는다.

이 문서는 기능과 동작 기준의 검토본이다. 다음 구현 계획은 대상 앱 확인 결과와 이 문서에 대한 사용자 의견을 반영해 작성한다.
