## 2. Shared rule and CSS ownership

B2 MUST add the following rule to **DESIGN.md → Application frame and content widths**, and synchronize the application-layout guide and consumer-agent instructions:

> The page root reserves scrollbar space. Shared full-page frames use `html { scrollbar-gutter: stable; }`, with one scrollbar-side gutter in classic mode and no reserved space in overlay mode. Header, main and footer use the resulting available page width. Changing page length or opening and closing a scroll-locking surface MUST NOT move those frames or their content horizontally. A consumer using a different document scroll policy MUST declare the documented root opt-out and own that policy consistently across routes.

1. **One implementation location:** `src/styles/components.css` MUST carry the root default in `@layer base` and the scoped lock correction in §3. `src/styles/globals.css` already imports `theme.css` and `components.css`; it MUST continue to obtain the rule through that import, without a second declaration. Home's `theme.css + components.css` path MUST obtain the same behavior. Generated `src/styles/theme.css` remains tokens only; do not hand-edit it or make a theme-only import change document scrolling. Component JS imports alone MUST NOT mutate `html`.
2. **Target/value:** the document `html`, not `body`, a header wrapper or `.ui-app-frame`; `stable`, never `stable both-edges`. Do not force `overflow-y: scroll`, hide scrollbars, subtract a hard-coded 15px, add a second body gutter or introduce JS viewport sizing. Classic gutter size belongs to the browser; 15px is the specified Mac test environment's measured size.
3. **Explicit opt-out:** `<html data-naeil-scrollbar-gutter="auto">` MUST set root `scrollbar-gutter: auto` and disable the shared lock correction together. The default root selector is `html:not([data-naeil-scrollbar-gutter="auto"])`; the opt-out is document-wide, present before first paint and unchanged while a modal is open. Consumers wanting a custom scroll container or another root policy use this opt-out first, then their own CSS. Overriding only `scrollbar-gutter` while leaving the correction enabled is unsupported. No new React provider, prop, CSS export or numeric token is required.
4. **Import impact:** the default applies whenever `components.css` is loaded, including apps using generic primitives; it is a deliberate 0.9.0 document-style change, not an implicit side effect of mounting NaeilHeader. Guides MUST make that impact and opt-out visible. The shared full-page profile uses an existing zero-margin, zero-outer-padding body; the patch MUST NOT add a body reset. Consumers with nonzero body edge spacing/custom root overflow use the opt-out and retain ownership of their frame/lock integration.
5. **Support/fallback:** in a browser supporting `scrollbar-gutter: stable`, both root and lock behavior MUST pass the gates. In an unsupported browser the declaration is ignored and the lock correction MUST NOT apply (`@supports (scrollbar-gutter: stable)` guard); existing Radix compensation remains. Overlay mode still computes `stable` in the default profile but reserves **0px**. Unsupported fallback is documented, not counted as a passing stable-reservation job.

## 3. Scroll lock: remove duplicate compensation, retain modal behavior

**Decision: one shared CSS correction, not changes to each menu/dialog or to Radix.** The locked dependency is `react-remove-scroll@2.7.2` / `react-remove-scroll-bar@2.3.8`. The latter injects `body[data-scroll-locked] { margin-right: <gap>px !important; --removed-body-scroll-bar-size: <gap>px; ... }` using the pre-lock viewport gap. A5 observed a long stable page's body shrinking **1425→1410→1425** while its fixed header frame remained 1425px. Header-only assertions miss the ordinary flow-content defect.

Under `@supports (scrollbar-gutter: stable)`, the correction MUST target only `html:not([data-naeil-scrollbar-gutter="auto"]) > body[data-scroll-locked]` and neutralize the duplicate **right margin to `0 !important` and `--removed-body-scroll-bar-size` to `0px`**. Use an unlayered selector with sufficient specificity to win when Radix injects its stylesheet later. The single `!important` is necessary to override the dependency's important margin and is a scoped frame/lock exception to the earlier chrome typography policy; do not broaden it to component styles.

- Radix MUST retain `overflow: hidden`, wheel/touch scroll prevention, overscroll handling, modal focus/inert behavior, Escape handling and its lock counter/cleanup. Do not set `modal={false}`, disable `RemoveScroll`, patch dependencies, observe the DOM with JS, or reset body width/position/padding to hide a shift.
- The correction is shared document policy: it also applies to a generic body Select, DropdownMenu or Dialog while the root reservation is active. Their typography/colors/spacing remain host-owned. A nonmodal navigation popover MUST remain nonmodal.
- Package chrome does not use the dependency's `right-scroll-bar-position`, `width-before-scroll-bar` or `with-scroll-bars-hidden` helper classes. Do not add blanket resets for them. Consumer-authored helper-class/custom lock systems are outside the default profile; document that they need their own integration or the root opt-out. B2 MUST recheck dependency output and package callers; a changed gap mode or new helper-class usage invalidates this mechanism until addressed.
- In **classic short and long pages**, capture closed → open → nested surface → inner close → final close, twice, for desktop account and locale, mobile sheet with account/locale, a generic body menu/Select/Dialog, and the existing sheet-to-confirmation handoff. Measure every surface that actually locks; also verify nonlocking popovers. No extra compensation may accumulate with nested locks; closing an inner surface MUST leave the outer lock effective; the final close MUST restore the unlocked body and scrolling.
- At every settled state and animation-frame samples through open/close, header/main/footer frame x and width, body x and width, centered settings/reading x and width, fluid/list right edge, and visible fixed controls MUST remain within **0.01 CSS px** of that document's pre-open values. Compare document-relative y only when focus/scroll offset is matched. Body right margin and removed-size variable MUST be 0 while locked in the default profile. Record padding, overflow, lock attribute/count, root/client/100vw widths and scroll offset; do not require `clientWidth` itself to stay constant (A5 observed it change without a frame shift).
- A gate MUST show the failing classic long-page body/content geometry without the correction, then pass with it. A short page alone, unchanged header alone, or a computed CSS declaration alone is insufficient. Opt-out and unsupported-browser branches MUST retain the dependency's original compensation rather than receive this zeroing.

## 4. Frame padding and Japanese 320px toolbar

**Keep all frame and chrome tokens unchanged.** `ui.width-frame = 1600`, `ui.frame-gutter = clamp(16px, 2.4vw, 40px)`, content caps, 48rem container breakpoint, sheet padding 24px, toolbar gaps, login padding and 44px targets remain as in 0.8.0. Available root space changes; component styling does not.

Record a real 100vw probe as well as raw computed padding. On the specified Chromium at width 1440, an untouched stable-root document uses a 1425px vw basis and nominal 34.2px padding (layout quantization may yield 34.1875px); a plain classic scrolling page without root reservation uses a 1440px vw basis and nominal 34.56px. A8's approximately 0.36px difference is explained by those different policies. B2 MUST compare equal root conditions; it MUST NOT change tokens, round away the difference or loosen the 0.01px paired tolerance to accommodate it. Other supported engines MUST be checked against their measured basis and paired controls rather than assuming Chromium's numbers universally.

For an LTR zero-margin default frame, let `A` be the available reserved-root width, `F = min(A, 1600)`. Frame x is `(A − F) / 2`; header/main/footer MUST agree. At 1440/390/320 classic with the validated 15px probe, `A` is 1425/375/305; overlay gives 1440/390/320. At 1920 classic, a 1600px frame starts at 152.5px; overlay starts at 160px. Padding still uses the existing vw expression and must stay stable through length and lock transitions. Explicit consistent frame overrides (including the existing 1100px/20px and utility overrides in `e2e/frame.spec.ts`) MUST continue to work. Horizontal overflow checks MUST use the effective layout width, not only `innerWidth`.

**F3 decision: accept and document the existing wrap; do not adjust spacing in this release.** With Japanese, signed-out canonical login content, width 320 and classic 15px reservation, sheet width 305 minus 48px padding leaves **257px** for a **261px** toolbar. The login moves to a second row: toolbar height **104px**. Overlay has 272px available and toolbar height **44px**. This is expected for naeil.dev's own default profile after adoption, including a short page. Gate both light/dark and short/long states; no clipped text, unreachable control, horizontal page overflow or target under 44px is permitted. All controls remain keyboard reachable within the sheet.

A5's isolated 12→10px login-padding experiment proves a possible 4px fit adjustment, but changes chrome styling and is **not selected**. Home LoginGate has no login slot/separator (approved F1); Home Workspace uses the account control. Their existing 44px toolbar heights remain. Keep rev 6's precise F3 auth-composition exception; do not make Home wrap or introduce a fifth Workspace chrome difference. A broader toolbar redesign or any extra wrapping waiver requires a separate owner decision.
