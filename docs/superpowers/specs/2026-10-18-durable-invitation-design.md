# Durable invitation transactions (local candidate)

The current Vercel site must retain the existing isolated `/auth/invite` flow across Node instances. This change prepares and tests that behavior locally; hosted settings, real users/mail/grants, deployment, DNS, SSO and language scope are unchanged. Existing frozen artifacts and SQL001–003 remain untouched.

## Selected approach

Use the existing central Supabase database through five service-role-only RPCs. A new SQL004 migration owns an RLS-protected `console_invite_transactions` table. The browser retains one random host-only HttpOnly cookie; only its SHA256 is stored. AES-256-GCM encrypts CSRF, invitation envelope and the verified candidate/JWT with a dedicated server-only key. A fresh 96-bit IV is used per write; additional authenticated data binds the format version and handle hash. The database sets an immutable ten-minute expiry, independently enforced on every RPC and before each authority step. No plaintext envelope/JWT enters an audit or outbox.

A local encrypted cookie alone would lack cross-instance atomic claims. Process memory cannot survive Vercel cold starts. The shared store provides both continuity and fencing without introducing another service or public hostname.

## State and concurrency

`empty → staged → verifying → candidate → verified → recorded → complete`, plus terminal `invalid` and `uncertain`. The encrypted payload contains transaction fields and a non-authoritative envelope identity (`id`, `version`, SHA256 of the canonical envelope); SQL phase governs permitted transitions. A claim checks the observed revision, assigns a random worker UUID, increments a monotonic fence and grants a thirty-second lease. Every checkpoint verifies owner, fence, revision, lease and absolute expiry, increments revision and renews the lease. Release removes ownership without replacing payload. Busy or stale claims are retryable503, never authority to invalidate the proof. GET/status performs no Auth verification or acceptance.

Persist `verifying` before `/verify`, and recheck absolute expiry immediately after the awaited checkpoint response before calling Auth. Immediately persist a validated candidate before `/user`, then persist verified identity, known verification receipt and completion as separate checkpoints. Candidate/verified/recorded can be reclaimed after a lost worker; a lease-expired `verifying` phase becomes `uncertain`, never a second `/verify`. A distinct uncertain state in ko/ja/en explains that the verification result cannot be recovered and asks the administrator to resend. It must not claim a known rejection. SQL never accepts a transition out of uncertain/invalid/complete.

An explicitly supplied resend envelope for the same invitation with a strictly higher version creates a separate transaction, handle, cookie, CSRF and expiry. It never claims or rewrites the previous row. The retained envelope identity distinguishes this case after proof/JWT secrets have been cleared; it does not authorize verification or acceptance. Identical, changed-at-the-same-version, older or different-invitation envelopes cannot replace an existing transaction. A new browser with an empty transaction can stage any otherwise valid envelope. Stale tab CSRF values fail before any mutation against a new cookie; an explicit old-cookie replay addresses only its previous row and existing SQL version authority rejects old proofs after resend. A new handle's cookie is returned after a known successful create, before later stage mutations, so a lost stage response can recover committed empty/staged truth without reopening the previous row.

The whole response may also lose that Set-Cookie, or create may fail before a new handle is known. The public script therefore retains this tab's parsed pending envelope through GET recovery even when the old cookie still reports staged, invalid or uncertain. GET cannot identify which envelope was staged. A deliberate **Prepare invitation** click restages the exact retained envelope; only its successful response clears the pending envelope. Auth verification still requires a separate later acceptance click. The retained envelope stays in tab memory, without URL, browser storage or GET side effects. Closing the tab requires reopening the original full invitation link.

Store response loss is ambiguous: do not retry mutations blindly or overwrite an unknown checkpoint. A later request reads committed truth. If a candidate checkpoint committed it resumes; otherwise a stranded verifying phase requires resend after its lease. Upstream `/user` failures retain the candidate. Unknown proof-recording outcomes repeat that idempotent RPC with the same identity. Acceptance only follows a persisted known-recorded checkpoint; an unknown acceptance outcome retries the existing acceptance RPC with the same JWT and session. Original replay receipts do not restore subsequently revoked grants.

## Interfaces

All functions return `{found, revision, fence, phase, payload, expiresAt, leaseUntil}` (missing/expired read returns `{found:false}`). Payload is a bounded versioned encrypted string. RPCs are `console_invite_tx_create(text,text)`, `console_invite_tx_read(text)`, `console_invite_tx_claim(text,bigint,uuid)`, `console_invite_tx_checkpoint(text,bigint,uuid,bigint,text,text)`, and `console_invite_tx_release(text,bigint,uuid,bigint)`. Only `service_role` has EXECUTE; all functions use empty search_path and check the claimed role. Direct table privileges are absent for anon/authenticated/service_role. At most4096 live transactions are retained; create opportunistically removes expired rows without evicting valid transactions.

`NAEIL_INVITE_CONFIG_JSON` is a private runtime alternative to the existing owner-only0600 external file. Exactly one source may be configured. The JSON source requires the four existing keys plus `transactionStore:"supabase"` and `encryptionKey` (canonical base64url encoding of32 bytes). Invalid JSON, duplicate keys, unknown fields, conflicting sources, weak/reused keys or oversized values fail closed. Vercel rejects legacy memory configuration; no failure falls back to a Map. File mode retains its existing path/ownership checks and may use the same explicit durable options outside Vercel. No `NEXT_PUBLIC` secret option is introduced.

## Authority and limits

The existing endpoint-specific typed denial parser and fixed subject/email/session checks remain authoritative. Existing SQL acceptance, version/cancel/resend/expiry/atomic grants/replay contracts are unchanged. Every authority call rechecks absolute transaction expiry. Encrypted JWT expiry cannot be extended; expired JWTs fail closed rather than using refresh or an unrelated browser session.

GoTrue `/verify` and a database checkpoint cannot commit atomically. If `/verify` consumes its OTP but its response or candidate checkpoint is lost, no safe token recovery exists: require explicit administrator resend. A worker paused after a live verifying checkpoint may start or finish an external request after its lease expires; fencing prevents its later checkpoints and no other worker re-verifies that phase. The immediately preceding expiry check narrows the window but cannot make a database lease atomic with GoTrue. Database unavailability and a missing/mismatched encryption key return503. Key rotation must preserve the same key across all instances for at least the ten-minute transaction lifetime, or deliberately drain/invalidate outstanding invitations. At-rest expiry erasure is opportunistic on create/read, not a claim of scheduled physical deletion.
