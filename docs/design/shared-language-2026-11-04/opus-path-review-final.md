# 첫 배포 롤백 보완 재검토 (sha256 `047d357d…f6e3`): 남은 차단 1건

## 결론

**제가 했던 가정을 에이전트가 바로잡은 것이 맞습니다.** 4단계부터 로컬 선택기, legacy redirect, 직접 입력만으로도 새 경로가 노출됩니다. 그러니 "외부 링크가 없으니 안전하다"는 전제는 틀렸습니다.

나머지 두 보완은 해결됐습니다.
- §4와 §11.4의 북마크 갱신 시점을 운영 수신 acceptance 통과 직후로 옮겼습니다.
- auth 로그인 진입과 return을 4단계에 포함했습니다.

**다만 새로 생긴 우선순위 하나가 서비스 가용성을 거꾸로 다룹니다.** 이 문장만 고치면 승인입니다.

## 차단 — §11 롤백 둘째 문단(140행)과 §12 "롤백" 행: 서비스 전체 503을 직전 운영 버전보다 우선함 (근거: 문서 추론)

**문제**
- 지금 문서의 순서는 호환 빌드 → 안 되면 서비스 전체 점검 503이고, 노출 이후에는 직전 버전으로의 복귀를 금지합니다.
- 직전 버전으로 돌아갔을 때 실제로 생기는 피해는 다음 정도입니다.
  - 새로 쓰인 `/ko`·`/ja` 경로가 404가 됩니다.
  - 접두사 없는 경로가 예전 해석(Estimate ja, Jev 저장값)으로 돌아갑니다.
- 반면 503은 모든 사용자의 업무를 막습니다. 언어 계약을 지키려고 서비스 전체를 멈추는 셈입니다.
- 롤백 문단의 "인증 누락" 우려는 옛 앱에 접두사 붙은 경로와 일치하는 보호 route가 있을 때만 성립합니다. 등록되지 않은 경로는 404이므로, 이는 사전 확인으로 판별할 수 있는 조건입니다.

**140행의 "같은 주소 의미·auth 경계를 유지하는 호환 빌드를 우선하며, … 기능 제공 실패를 명시한다." 부분을 다음 문장으로 바꿉니다:**
> 같은 주소 의미·auth 경계를 유지하는 호환 빌드를 우선한다. 이를 제공할 수 없으면 직전 운영 버전으로 복귀하되, 그 버전이 `/ko`·`/ja`·locale이 붙은 protocol 경로에 보호 데이터 없이 404를 응답하는지 사전에 확인해 두어야 한다. 이 복귀는 언어 계약 실패와 접두사 없는 경로의 의미 역전으로 기록하며 완료 상태를 철회한다. 요청 언어의 점검 503은 직전 버전도 안전하지 않을 때만 쓴다.

**같은 문단의 "실제 노출 후에는 … 구버전 단독 복귀를 허용하지 않는다"는 다음 문장으로 바꿉니다:**
> 실제 노출 후 구버전 복귀는 위 사전 확인을 통과한 경우에만 허용하며, 정상 rollback 성공으로 세지 않는다.

**§12 롤백 행에 추가합니다:**
> 직전 버전의 prefixed 404·비노출 사전 확인

이 수정 외에 이번 변경에서 생긴 다른 모순은 없습니다. 이번 재검토에서 한 일은 로컬 문서 열람과 hash 확인뿐이고, 파일 변경이나 추가 탐색은 하지 않았습니다.
