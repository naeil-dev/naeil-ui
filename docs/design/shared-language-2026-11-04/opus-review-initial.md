이 파일은 Opus 5.5의 1차 최종 답변을 보존한 기록이다. 중간 추가 질문 때문에 나뉜 답변 조각을 연결했고 질문·내부 분석은 제외했다. 모든 제안을 그대로 채택한 문서가 아니며, 사실 확인과 조정 결과는 [반영표](opus-review.md)가 우선한다. 특히 브라우저 수명의 정확한 일수는 이번 외부 조사로 검증된 사실이 아니다.

# 공통 언어 처리 설계 초안 독립 리뷰 (Opus 5.5)

검토 대상: `docs/superpowers/specs/2026-11-04-shared-language-design.md` (sha256 `ab9991d7…6321`). `/tmp/…/design-review-draft.md`와 내용이 같습니다. 파일은 읽기만 했습니다.

## 결론

**공통 계약에 경로/query 어댑터를 붙이는 핵심 권고는 채택해도 됩니다.** 다만 초안이 든 이유가 약하고, 실제로 구현할 수 없는 약속이 2~3개 있습니다. 아래 차단 항목을 고친 뒤에 최종본으로 확정하는 것이 좋습니다.

- **"경로가 베스트 프랙티스"라는 근거는 없습니다.** 근거 문서(R1)는 검색에 노출되는 공개 콘텐츠에 언어별 URL을 쓰라는 것이고, 인증 앱에 경로를 쓰라는 근거는 아닙니다.
  - Google 비교표에서 parameter 방식이 '권장하지 않음'이었던 것으로 기억합니다. 하지만 ledger에서 그 셀이 유실됐으므로 근거로 인용하면 안 됩니다. 어차피 공개 검색 대상이 아닌 앱에는 해당하지 않습니다.
- **모든 서비스를 경로로 옮기지 않는 진짜 이유는 초안 §2에 쓴 것과 다릅니다.** Jev의 root-only 검증기는 `/`, `/ko`, `/ja` 세 개를 허용하도록 고치면 되는 작은 변경입니다. 실제 비용은 두 가지입니다.
  1. App Router에서 `[locale]` 세그먼트가 바뀌면 그 아래 트리가 다시 마운트됩니다. 그래서 Jev 스트림과 Estimate 편집 상태를 지키려면 middleware rewrite와 pathname replaceState 같은 우회가 필요합니다.
  2. Estimate의 기존 접두사 없는 URL(지금은 일본어)이 영어 URL로 의미가 바뀝니다.

  §2를 이 두 가지로 다시 쓰고, 나중에 주소를 통일하고 싶으면 서비스별 `urlStrategy`만 바꾸면 된다고 적으면 충분합니다.
- **사용자 선호(영어는 `/`, `/ko`, `/ja`)는 공개 메인에 그대로 적용하는 것이 맞습니다.** 앱에서 `?lang=en`을 생략하지 않는 규칙도 맞습니다. 앱에서는 lang이 없는 주소를 "언어 미지정"으로 해석하기 때문입니다.

## 차단 항목 (최종본 전에 수정)

**B1. §4·§8: 루트 동작 변경과 메인에서 쿠키의 역할이 정의되지 않음**
- 지금 배포된 메인은 locale detection이 켜져 있어서, 한국어 브라우저로 `/`에 들어오면 `/ko`로 이동합니다. 초안은 이 동작을 없앤다고 기록하지 않았습니다.
- 그 결과가 연쇄로 이어집니다. 한국어 사용자가 naeil.dev를 직접 입력하면 영어 화면이 열리고, 여기서 앱으로 가는 링크에 `?lang=en`이 붙어 사용자가 저장한 ko 선호를 덮습니다.
- 수정안:
  - `/`는 항상 영어로 유지합니다. 추정 언어로 자동 이동하지 말라는 R1, R8과 맞습니다.
  - 메인에서 쿠키의 역할을 "이동하지 않는 제안"으로 정합니다. 명시적으로 저장한 선호가 현재 페이지 언어와 다르고 그 번역이 있으면 "한국어로 보기" 링크 하나만 보여줍니다. Accept-Language로는 제안하지 않습니다.
  - 이 동작 변경을 의도한 변경으로 rollout 기록에 남기고, 인수 조건에 넣습니다.
  - 이렇게 하면 쿠키의 역할이 두 가지로 분명해집니다: ① 언어가 없는 앱 진입(북마크, 직접 입력, 기존 Estimate 링크), ② 메인의 제안 링크.

**B2. §6·§9: query 앱에서 SSR의 `html lang`과 metadata를 맞춘다는 약속은 지금 쓰인 방식으로는 구현할 수 없음**
- App Router의 root layout은 `searchParams`를 받지 못합니다.
- 수정안:
  - 각 앱의 proxy/middleware가 query → 공통 쿠키 → Accept-Language → 서비스 기본값 순으로 언어를 정하고, 요청 헤더(예: `x-naeil-locale`)로 넘깁니다. layout은 `headers()`로 읽습니다.
  - middleware는 Set-Cookie를 하지 않습니다.
  - 클라이언트에서 언어를 바꾸면 provider와 함께 `document.documentElement.lang`, `document.title`도 직접 갱신합니다.
  - Jev의 legacy localStorage는 서버가 읽을 수 없습니다. 그래서 공통 쿠키가 없을 때만 클라이언트의 중립 로딩 상태에서 확인합니다.

**B3. §7·§10: 패키지 버전 문제가 빠져 있음**
- source-audit 기록으로는 Jev와 Estimate가 UI 0.7.2, Site가 0.9.0입니다. 새 entry `@naeil/ui/naeil-locale`은 그 이후 버전에 들어갑니다.
- 그러면 이 entry를 쓰려면 Jev와 Estimate를 0.7.2에서 새 버전으로 올려야 하고, 그 사이의 header/footer 변경도 함께 들어옵니다.
- 수정안: §10에 "소비 앱 패키지 업그레이드와 header/footer/account 동등성 재검증"을 독립 단계로 넣습니다.
  - 이 업그레이드를 하지 않으려면 대안은 공통 test vector JSON과 앱별로 약 50줄짜리 구현입니다. 그래도 권고는 패키지 entry와 명시적 업그레이드입니다.

**B4. §10.4: rollout을 실행할 수 없음**
- "레지스트리에 어댑터 채택 여부를 표시하고 모두 준비되면 활성화"하려면 배포 상태를 발행된 패키지에 넣게 됩니다. 실행 방법도 정해져 있지 않습니다.
- 수정안: **받는 쪽을 먼저, 보내는 쪽을 나중에** 배포합니다.
  1. Estimate가 삼국어 UI와 `?lang` 수신을 갖춥니다.
  2. Jev를 공통 resolver로 바꿉니다.
  3. 마지막에 메인과 앱의 링크 builder 및 쿠키 쓰기를 켭니다.
- 구버전 앱은 모르는 `lang` query를 무시하므로 링크가 먼저 나가도 해가 없고, 롤백도 구조상 안전합니다. 레지스트리의 채택 상태 필드는 삭제합니다.

## 중요 수정 (차단은 아니지만 최종본에 반영)

**M1. §6: Safari에서는 1년 수명이 보장되지 않음**
- Safari ITP는 `document.cookie`로 쓴 영속 쿠키를 7일로 제한합니다.
- 수정안: 언어를 명시적으로 선택하면 같은 origin의 작은 route handler나 Server Action이 서버 `Set-Cookie`로 씁니다. B2로 서버가 언어를 정하게 되므로 클라이언트에서 쿠키를 읽을 필요가 없어지고, HttpOnly도 쓸 수 있습니다(필수는 아님).
- 이 방식이면 "쿠키를 쓰는 곳은 이 endpoint 하나"라는 단일 시험 항목이 생깁니다. 응답 중 이 endpoint만 `naeil_locale_v1`/`NEXT_LOCALE` Set-Cookie를 낸다는 것 하나로, prefetch·RSC·SSR·Action 관련 부작용 검사가 대부분 해결됩니다.

**M2. §6: 중복 쿠키를 무효로 처리하면 복구할 방법이 없음**
- 같은 이름의 host-only 쿠키가 남아 있으면 선호값이 계속 무효로 남습니다.
- 수정안: 명시적으로 쓸 때 현재 호스트의 host-only 같은 이름 쿠키도 `Max-Age=0`으로 만료시킵니다. 이 내용을 인수 조건에 추가합니다.

**M3. §5·§8: next-intl이 `/en`을 실제로 생성함**
- 로컬에 설치된 next-intl 4.8.3 소스를 확인했습니다.
  - `useRouter().replace(..., {locale})`는 `forcePrefix`로 `/en/...`을 만든 뒤 middleware 리다이렉트를 거칩니다. 현재 `src/components/nav-wrapper.tsx:24`가 이 경로를 씁니다. 따라서 "`/en`을 생성하지 않는다"는 문장과 실제 동작이 다릅니다.
  - Link onClick과 router의 push/replace/prefetch, middleware의 `syncCookie`는 모두 `localeCookie: false`이면 쿠키를 쓰지 않습니다. 설치 버전 기준으로는 §8의 확인 항목이 충족됩니다. 배포된 버전이 같은지는 따로 확인해야 합니다.
- 수정안:
  - 언어 선택기는 builder가 만든 최종 href로 locale 옵션 없이 이동합니다.
  - `/en` 처리는 next-intl 기본값인 307을 그대로 둡니다. 영구 리다이렉트 커스텀은 삭제합니다.
  - 메인의 `lang` query 제거 규칙도 삭제합니다(무시하면 충분합니다).

**M4. §8 Estimate: 미정 항목 결정**
- 서비스별 `defaultLocale`을 둡니다. Estimate의 최종 fallback은 **ja**로 해서 기존 사용자가 갑자기 영어를 보지 않게 합니다. 나머지 서비스는 en입니다.
- 표시 포맷은 UI 언어를 따르는 `Intl`을 씁니다. 통화, 시간대, 문서 언어는 데이터에 고정합니다.
- en/ko/ja는 소수점과 자릿수 구분자가 같으므로 입력 파싱은 바뀌지 않는다고 명시합니다.
- "별도 정책으로 유지" 같은 미결 표현은 남기지 않습니다.

**M5. §3·§11: 적용 범위의 끝이 정해져 있지 않음**
- "이후 추가되는 활성 사용자 페이지"와 "기타 활성 owned UI 필수"가 있으면 완료 조건을 정할 수 없습니다.
- 수정안:
  - 1단계 산출물로 날짜가 찍힌 inventory를 만들어 필수 범위를 고정합니다. 출처는 tunnel ingress, DNS, 배포된 route 목록입니다. 이후 추가는 amendment로 처리합니다.
  - 앞으로 추가될 페이지는 완료 조건이 아니라 계약 시험으로 막습니다(모든 owned href가 builder를 거치는지).

**M6. §11: 인수 조건의 링크 범위가 실제와 다름**
- "메인 ↔ Jev ↔ Estimate 모든 방향"은 존재하지 않는 링크를 가정합니다. 헤더 catalog는 `/design` 하나뿐입니다(`src/components/naeil-header-content.ts:6-14`).
- 수정안: inventory에 있는 실제 링크 각각 × 3개 언어 행렬로 바꾸고, 새 교차 링크를 만들지 않는다고 명시합니다.

**M7. §9: 전환 단계를 단순화**
- Estimate와 Jev는 3개 언어 메시지를 정적으로 번들합니다. 그러면 "메시지 준비 실패 → 이전 화면 복원 → stale operation 무시"라는 분기가 대부분 사라집니다. 크기가 실제로 문제라고 측정되면 그때 lazy로 바꿉니다.
- query 앱의 언어 전환은 navigation이 아니므로 guard를 거치지 않는다고 단정합니다.

## 가벼운 보완

- **L1. §3:** 레지스트리의 `basePath`/longest-match는 지금 대상이 없으니 삭제합니다.
- **L2. §5:** popstate로 이전 history 항목에 돌아가면 그때의 언어가 보입니다. URL을 권위로 삼는 이상 피할 수 없는 동작이므로, 의도된 동작으로 명시하고 시험합니다.
- **L3. §8:** query 앱의 인증 화면은 noindex로 두고 hreflang/canonical을 붙이지 않습니다. 공개 페이지가 생기면 그때 lang이 포함된 canonical을 씁니다.
- **L4. §4:** 번역이 없는 언어로 들어오면 404를 응답하고 존재하는 버전의 링크를 보여줍니다. 영어 내용을 `/ja` 아래 200으로 보여주는 것은 금지라고 응답 방식을 확정합니다.
- **L5. §10.6:** Jev legacy 읽기(중립 로딩)를 끝내는 날짜를 정합니다.
- **L6. §9:**
  - 기존 `loginErrorLocation`이 locale을 보존하고, `canonicalRedirect`가 정확한 origin 세 개만 허용하는 것을 확인했습니다. 이 둘을 유지하면 됩니다.
  - 로그인 페이지 언어는 메인 경로(`/ko/login`)가 정하고, `next` 안의 lang은 복귀한 앱만 사용한다고 명시합니다.
  - `src/proxy.ts:43-49`의 보호 경로 리다이렉트는 locale을 잃고, 503 응답은 영어 평문입니다. 하지만 이 코드는 라우팅되지 않는 `_archive`의 `/sa/reports`에만 해당하므로 **현재 결함이 아닙니다.** 다시 살릴 때만 고치면 됩니다.

## 근거 없는 가정

1. §2는 Jev 검증기를 이관 비용의 주된 근거로 들었습니다. 위에서 본 대로 실제 비용은 재마운트와
Estimate URL 의미 변화입니다.
2. Estimate의 최종 기본값 en. 기존 ja 사용자에게 regression이 됩니다(M4).
3. 패키지 버전 출처가 맞지 않습니다. 이 branch의 `package.json`은 0.7.2인데 관측된 Site는 UI 0.9.0입니다. 구현 기준이 되는 소스를 1단계에서 정확히 지정해야 합니다(§10.1의 취지는 맞지만 버전 이야기를 명시해야 함).
4. R13(dev-server 관찰)은 이번에 로컬 4.8.3 소스를 직접 확인한 결과로 대체됩니다. 그래도 배포 버전과 같은지는 별도로 확인해야 합니다.
5. §12에 이 리뷰를 기록할 때, 위의 next-intl 확인은 로컬 `node_modules`를 읽은 결과이고 실행 시험이 아니라는 점을 구분해 적어야 합니다.

이번 검토에서 파일 생성·수정·설치·로그인·웹 조사는 하지 않았습니다.
