## 남은 차단 — §6 끝 문단과 §9 첫 문단: query 앱에서 언어를 바꾼 뒤 서버 렌더 문구가 옛 언어로 남음

**문제**

- query 앱의 언어 전환은 `replaceState`와 client provider 갱신으로 끝납니다. 또 §6은 "이후 query 언어 변경은 RSC fetch에 기대지 않고"라고 적었습니다.
- 그런데 layout이나 page의 **서버 컴포넌트가 `x-naeil-locale`로 렌더한 문구**(표 머리글, 빈 상태, 오류 문구 등)는 다시 렌더되지 않습니다.
- 그 결과 Estimate·Jev 화면에 두 언어가 섞입니다. 지금 문서에는 이를 막는 규칙도, 인수 조건도 없습니다.

**§9 첫 문단 끝에 추가할 문장**
> query 앱의 번역 문구는 locale 전환 후 같은 화면에 이전 언어가 남지 않아야 한다. 서버 컴포넌트가 초기 locale로 렌더한 문구는 client provider로 렌더되는 컴포넌트로 옮기거나, commit 직후 `router.refresh()` 1회로 새 locale의 서버 payload를 받아야 한다. 후자를 택하면 편집 입력·dirty·undo/redo·Jev 스트림이 그대로 유지됨을 같은 인수 항목으로 확인한다. 두 방식 중 무엇을 썼는지 서비스별 receipt에 기록한다.

**§11 데이터 보존 행에 추가할 항목**
> 언어 전환 직후 대표 화면 전체에서 이전 언어 문자열이 0건

## 정확한 문장 수정 (차단은 아니지만 문서 안의 모순)

1. **§3 표의 메인·Jev 행:** "이후 추가되는 활성 사용자 페이지"와 "이후 추가되는 사용자 경로"는 본문의 고정 inventory 원칙과 맞지 않습니다.
   - 메인 행은 "고정 inventory의 활성 사용자 페이지(이후 추가분은 같은 계약 검사 대상)"로 바꿉니다.
   - Jev 행도 같은 방식으로 바꿉니다.
2. **§9 셋째 문단(메인):** 메인은 navigation이 끝나기 전에 쿠키를 쓰므로, 조정 #6("전환 성공이 확인된 명시 의도에만 기록")과 어긋납니다. 이 순서를 바꿀 필요는 없고, 예외라고 명시하면 됩니다.
   > 메인은 route navigation 특성상 guard 수락 직후 기록하는 명시적 예외다. 이후 이동이 실패해 선호와 페이지 언어가 달라지면 §4의 비강제 제안 링크로 복구된다.
3. **§6 `x-naeil-locale` 문단:** 다음 문장을 추가합니다.
   > layout도 이 헤더 값을 `parseLocale`로 다시 검증하며, proxy matcher가 제외하는 경로에서는 이 헤더를 신뢰 입력으로 쓰지 않는다.

   위조된 헤더로 할 수 있는 일은 요청자가 자기 화면 언어를 고르는 것뿐이라 위험은 낮습니다. 다만 검증 위치는 명시해야 합니다.
