# URL 통일안 재검토 (sha256 `8394d8e0…645d`): 승인 조건 1건

## 결론

**B1과 B2는 해결됐습니다. 남은 차단은 없습니다.** 다만 B2 보완에서 롤백과 관련한 작은 모순이 하나 생겨, 아래 문장 하나를 반영하는 것을 승인 조건으로 둡니다. 반영하면 최종 설계로 확정해도 됩니다.

## B1 해결 확인 (근거: 문서 열람)

- §5 셋째 문단이 client 이동, 서버 redirect, form/Action 후 이동, 로그인 return을 모두 builder 대상에 넣었습니다.
- 서버는 요청 locale, client는 provider locale을 쓰도록 출처가 구분되어 있습니다.
- 지적했던 Estimate 사례(`/ko`에서 `/ko/estimates`로 보내는 redirect)가 문서에 그대로 들어갔습니다.
- protocol endpoint 제외, §11.1 inventory, §12 "전체 연결" 행까지 반영됐습니다.
- `revalidatePath`를 단정하지 않고 실제 cache key를 검증하도록 한 판단이 더 정확합니다.

## B2 해결 확인

- 대안으로 택한 "4단계 수신 배포 시점부터 접두사 없는 경로 = en"을 수용합니다.
- 제가 제안한 임시 설정에는 에이전트가 지적한 두 문제가 실제로 있습니다(추론으로 동의).
  - `/?lang=en`이나 `/en`을 `/`로 정규화하면 다시 ja로 해석될 수 있습니다.
  - 롤백할 때 이미 공개한 영어 `/`의 의미를 다시 뒤집게 됩니다.
- 의미가 바뀌는 시점은 §4와 §11.4에 서비스별로 명시됐고, §11.5의 "다시 바꾸지 않는다"와 롤백 문단도 서로 일치합니다.

## 승인 조건 — §4 마지막 문단, §11.4, 롤백 문단: 북마크를 배포와 함께 갱신하면 첫 배포 롤백이 막힘 (근거: 문서 추론)

**문제**
- §4와 §11.4는 일본어 북마크와 문서 링크의 `/ja/…` 갱신을 수신 버전 배포와 "함께" 적용합니다.
- 롤백 문단은 "새 링크가 배포된 뒤에는 옛 앱으로 단순 복귀하지 않는다"고 합니다.
- 두 규칙을 합치면, Estimate나 Jev의 **첫 4단계 운영 배포 자체가 실패했을 때** 돌아갈 곳이 없습니다.
  - 이전 버전은 `/ja`를 모르므로, 갱신된 북마크가 404가 됩니다.
  - 그렇다고 4단계 버전은 실패한 그 버전입니다.

**§11.4의 "일본어 문서/북마크 갱신본을 함께 적용한다"를 다음 문장으로 바꿉니다:**
> 일본어 문서/북마크 갱신본은 해당 서비스의 4단계 운영 수신 acceptance가 통과된 직후 적용한다. 그 전에는 외부에 `/ko`·`/ja` 링크가 없으므로, 첫 수신 배포 실패 시 직전 운영 버전으로 단순 복귀할 수 있다.

**§4의 같은 내용도 맞춰 바꿉니다:**
> 갱신본을 준비하고 해당 서비스의 §11.4 수신 acceptance 통과 직후 적용한다.

이렇게 바꾸면 배포 직후 짧은 기간 동안 일본어 사용자가 `/`에서 영어와 비강제 제안 링크를 보게 됩니다. 이는 §4가 이미 의도한 변경 범위 안입니다.

## 선택적 명확화 (차단 아님)

§11.4는 "Estimate return 생성 반영"을 4단계에, "다른 서비스로 보내는 새 링크"를 5단계에 두었습니다. 그래서 로그인 링크(`naeil.dev/ko/login?next=…`)가 어느 단계에 속하는지 애매합니다.

다음 문장 하나로 정리할 수 있습니다:
> 로그인 진입 링크와 return 생성은 auth 경계이므로 4단계에 포함한다.

이번 재검토에서 한 일은 로컬 문서 열람과 hash 확인뿐입니다. 파일 변경, 실행 시험, 외부 탐색은 하지 않았습니다.
