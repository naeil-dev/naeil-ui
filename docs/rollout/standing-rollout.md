# Standing rollout for naeil.dev, Estimate and Jev

The owner requested all three follow-ups on2026-10-23: maintained documentation, public frozen UI0.7.1, and continuous service rollout. Home Console and Baby remain excluded. The [design](../superpowers/specs/2026-10-23-standing-ui-release.md) and [implementation checklist](../superpowers/plans/2026-10-23-standing-ui-release.md) describe this work. Operational activation and publication receipts are recorded separately; implementation alone is not an enabled job.

## Package, site and automation sources

The npm0.7.1 archive stays byte-identical to frozen source `32108fd8e1cb1db6dae24a09f3ca72ac9a91f618`, SHA256 `ecd656c595fd63516417eef58a5e2624d1f1bf928ba0465761292d05502ab3f8`. Its tag is `v0.7.1`. That old package source must never replace the website's newer shared-login source.

The existing Vercel Git integration deploys reviewed application main. Each release manifest separately binds `siteSourceRevision`, an immutable `siteArchive` made by packing that exact site source, and `siteRuntimeSha256`. `package-runtime.mjs` compares every public runtime/export/style/contract file and resolver, platform and dependency metadata against the frozen npm package; only `README.md`, `DESIGN.md`, `CHANGELOG.md` and Markdown under `docs/` may differ. The maintained site archive is evidence, not another npm0.7.1 upload.

The local worker runs a fixed reviewed automation checkout, independent of either release source. GitHub Releases provide data and exact assets, never executable commands or native configuration. Public repository PR workflows do not run on the production host.

## Authorized automatic lane

Only `naeil`, `estimate`, `jev` execute, in that order. [standing-services.json](standing-services.json) contains concrete production routes, locale/auth states and anonymous central-login probes. It explicitly describes representative live chrome coverage; parameterized business records and mutation/save/stream scenarios remain isolated consumer test gates. Historical discovery of other domains stays in [services.json](services.json).

Initial0.7.1 adoption verifies the actual current shared-session artifacts, archives/manifests, ownership, protected/public routes and independent chrome/account references. It does not fabricate a0.7.0 predecessor or adopt the retained password-auth application as an automatic recovery target.

Ordinary unattended changes begin with consecutive0.7.x patches, contract1, fix-only release classification and an unexpired private policy. A frame/DOM/guard patch additionally needs a private `reviewedMigration` approval for that exact release and every selected service (see [automation.md](automation.md)); without it the worker blocks the release. The chosen initial operational window is90days through0.7.99. Contract/API/DOM changes and expired authorization stop for a reviewed migration. The release publisher still produces and validates each new package/reference; the worker then updates the selected services without per-app manual deployment commands.

That general policy does not make the configured 0.7.2 continuation a later-release worker. This active generation binds the exact 0.7.2 release, concrete candidate receipts and one Estimate successor attempt. It cannot execute 0.7.3, **even before the current authorizations expire**. A separately reviewed future preparation, authorization and activation workflow must bind the next candidate, configuration, generation, attempts and actual predecessors. The exact adopted source record can be reused as provenance without another source review; it does not supply that execution authority. The later dependency-only **execution** criterion in change-management spec §6/§12 remains unmet/deferred, not waived or satisfied by source-helper tests. This fix supplies no generic rebind/skip workflow and does not relax the current release or attempt fences.

## Execution and recovery

The launchd worker polls published stable releases on the existing host, freezes the exact tag/asset identities, validates package and reference hashes, and records an invocation before dispatch. It first proves the exact Git/Vercel website source and live UI, then runs each native consumer's update, test, build, package, managed activation and production check. Native clones come from the private remotes; Estimate uses the filtered history and source SHA correspondence map.

Native adapters bind dedicated runtimes, current manifests, process/listener/lock ownership and unchanged configuration. They preserve business data and stop/start only the owned service naturally. Jev takes a SQLite backup with a scratch restore proof; Estimate captures private copies of its data and backups, reads every copy back against the snapshot hashes, restores them into a scratch directory to prove the bytes and schema3 revision (`proof.json`), and verifies the live bytes are unchanged before and after the transition. Neither proof restores over live data. Automatic recovery selects only the exact verified shared-session-compatible predecessor. It changes code and preserves the latest data. Current/previous/failed releases and recovery evidence are retained.

The shared STOP file blocks new stages; it never abandons a stage already in flight. The dispatcher records `stopped` (or `authorization-expired`/`disabled`) in its summary without creating a durable block, and resumes from the same release record once STOP is removed. Before any change, Estimate reports STOP as `deferred`; after its consumer source update it reports `gate-failed` with `stopped-after-source-update` (runtime untouched). Once the Estimate bridge has requested the service stop, it completes the bounded switch and start despite STOP or approval expiry, or keeps the durable phase for recovery. Jev's native transaction already restores its previous code after a failure that follows the stop.

When an Estimate activation fails after the stop has begun, the adapter recovers automatically only if the retained marker belongs to this exact attempt's activation, its phase is a known pre-verification phase, `current` points to the predecessor or candidate, STOP is absent and the code-only rollback approval is active. It then runs the bridge `recover` action bound to the marker digest and verifies the predecessor in production. Any other condition keeps `activation-pending`, the lock and the marker for an operator.

A dispatched command with uncertain completion remains stopped for reconciliation; removing a lock/marker is not a retry strategy. A nonzero exit with a bound, owner-only result of `gate-failed`, `activation-pending`, `review-required` or `not-deployed` is recorded as that result. Missing, unbound or timed-out output stays `uncertain`. Estimate idempotency ledgers record terminal outcomes and retain earlier ledgers as history files; a proven pre-change deferral is retried on the next poll. If cached evidence for an earlier service is older than `maxEvidenceAgeSeconds` while a later service still runs, the dispatcher re-verifies the same artifact read-only and appends the new receipt; failure blocks with `cached-evidence-reverification-failed`. No force kill, lease deletion, data initialization, historical database restoration or fallback to retired authentication is part of rollout.

The website observer correlates successful Git deployments with the current public identity. An early CI or deployment failure does not prove which artifact is live; recovery requires a fresh identity and platform inspection. A site failure stops native rollout and retains its result for operator recovery through the existing platform. The observer does not perform Vercel rollback.

## Explicit 0.7.2 generation continuation

The [change-management spec](../superpowers/specs/2026-10-26-standing-rollout-change-management.md), together with the exact recorded approval, governs generation changes. The APIs in [standing-transition.mjs](../../scripts/rollout/standing-transition.mjs) implement only the retained source-only Estimate 0.7.2 failure: `planTransition(input)` is pure and returns a reviewable diff plus `planSha256`; `applyTransition(plan, approval)` stages a new epoch and cuts over; `recoverTransition(plan, approval, recoveryApproval)` resumes an exact interrupted phase. There is no generic rebind, skip or supersede command. These are library APIs, not installed operational commands or permission to execute a draft.

Before apply or recovery, all of these conditions must hold:

- The canonical `~/.local/share/naeil-ui-rollout/STOP` remains present, private0600. The old scheduler has an explicit disabled override **and** is absent from its exact GUI domain. The tool never disables or installs a job itself. Owner approval to stop the old launcher is separate preparation; STOP alone cannot fence r5 state writes.
- Approved canonical launchctl, ps and lsof bytes prove the exact missing-service diagnostic, disabled override, absence of matching dispatcher/adapter/native/verifier children and absence of open handles in every dispatcher/native state root. Required locks, pending intents and Estimate markers are absent. Unknown output or an arbitrary nonzero exit is refusal, not proof.
- The live legacy state equals the exact retained snapshot. The original Estimate request/output and same release/service ledger prove `gate-failed`, source mutation only and `runtimeMutationAttempted:false`. The native predecessor identities match exact production-verified baseline evidence and fresh public identities. Jev remains unstarted for this release. Every retained Jev native transaction is pinned together with its original native request/output, adapter result/configuration, predecessor baseline and artifacts. Only independently validated `active`, `recovered` or `rolled-back` history is accepted; unfinished, uncertain, unknown or unbound history blocks without deletion.
- New source approvals, adoption records, immutable candidate receipts, both service execution contexts and all referenced adapter/verifier configuration bytes match the plan. The top-level configuration, source snapshot, previous approval digest, published release identity, old/new generations, state roots, epoch and new Estimate attempt are exact approval inputs.

The successor approval has kind `standing-continuation-approval`, action `continue-0.7.2-after-source-gate-failure`, and binds `planSha256`, `previousApprovalSha256`, explicit `successorOf`, `releaseSha256`, operational generation, original/new Estimate attempt, approver/reference and bounded dates. The original `reviewedMigration` record and published tuple stay unchanged. **Both** the successor approval and the original migration expiration, `2026-11-01T21:00:00Z`, bound execution. Changing successor dates cannot extend that original window. Operation after expiry needs a separately reviewed renewed authorization path, outside this continuation implementation. Source adoption remains provenance, not execution permission.

One exclusive `control.lock`, outside both epochs, protects transition and polling. Its first durable write includes `acquisition`: a transition acquisition embeds the exact plan and approval before any await, while an active-generation acquisition pins the exact pointer and completed journal references. Acquisition records an unvalidated purpose, never a completed phase. Immutable plan/approval/phase/probe records stay in `control/transitions/<planSha256>/`, alongside byte-exact historical Estimate ledger/native baseline copies and `validated-root.json`; a small fsynced `transition.json` records `prepared`, `imported`, `continuation-intent`, `validated`, `cutover-intent`, `cutover`, then `completed`. Every incomplete phase blocks the launcher, including a new active pointer with an unfinished journal. Cutover atomically replaces `active.json`, binding exact top-level config bytes, referenced-config manifest digest, generation and state epoch. Old pointer/state/output/artifact/native records are retained. The tool leaves STOP present and performs no native action.

Completed imports are validated and reused against their original source, manifest, immutable imported root and evidence inventory. An importer is never run again into nonempty output. Partial/conflicting imports remain for review. Continuation preserves the original release binding and naeil request/result, appends the original Estimate failure to history, and authorizes one distinct Estimate attempt with the unchanged idempotency key and exact `reconciliation.priorAttemptId`. It does not rewrite native baselines, markers or ledgers.

An interrupted phase requires a new `standing-transition-recovery-approval` binding the exact plan/approval digests, current `transition.json` reference, phase and current pointer byte digest (or null), with approver/reference and bounded dates. Admission checks those exact initial bytes once; approved journal/pointer progression does not renew the immutable recovery authority. Authority is rechecked after awaited prerequisites/probes and before phase/pointer writes. Loss of recovery, continuation or original migration validity retains the completed boundaries, STOP and control lock for explicit review. Other thrown test exceptions release the control lease; real process death can leave it behind. Recovery never steals that lock.

After separately proving the exact owner process has exited, `archiveTransitionLock(plan, approval, archiveApproval)` is an explicit prerequisite. Kind `standing-control-lock-archive-approval` binds `planSha256`, `approvalSha256`, exact private `controlLock` and `stop` file references, `journal` (or explicit null), `pointerSha256` (or null), `current` (or null), approver/reference, bounded dates and unrevoked status. The control lock itself binds the acquisition bytes. The absent-journal case requires a bound transition acquisition, unchanged old pointer/snapshot/native predecessors, no successor epoch contents and `current:null`. It preserves the unvalidated acquisition without fabricating a journal; after archival, a separately invoked apply still needs its original current authority. An incomplete journal uses its exact phase and pre-cutover evidence, with `current:null`.

For a completed journal, `current` instead pins the current epoch's `state`, `binding` and immutable `validatedRoot` references; `history:{estimateLedger,estimateBaseline,jevBaseline}` references with the original planned bytes; `estimate:{baseline,ledger,priorLedger,result,dispatches}`; and `jev:{baseline,result,transactions}`. File references contain exact canonical `path`, `sha256` and `bytes`. `result` is null for an unstarted consumer; `dispatches` is the exact Estimate native `dispatch.json` reference inventory; `transactions` uses the plan's complete Jev request/result/config/predecessor/transaction reference schema, adding only the bound current successor. Current terminal success must agree with the retained execution request, transport output, adapter result, native responses/transactions, baseline, production identity and current public identity. Estimate's prior ledger must remain in the adapter's actual history file after successor progress. Historical baseline/ledger copies prove their original bytes without requiring mutable current paths to stay pre-transition. Unstarted consumers retain their exact predecessor evidence. Unsupported failures, nonterminal/unknown/unbound native work, pending verification/intents, locks or markers remain blocked for explicit reconciliation. Archival performs no native call, transition replay or ledger/baseline rewrite.

Pinned raw quiescence and owner-process inventories must exclude the recorded PID, including PID reuse, and matching children. Archival proof schema2 is a small index bounded at256KiB: exact `path`/`sha256`/`bytes` references bind separate acquisition (256KiB), quiescence metadata (2MiB) and final owner-observation metadata (256KiB) JSON records. Both distinct process observations retain each stdout/stderr as an immutable raw UTF-8 leaf, bounded at1MiB; `readArchivedControlStream` verifies private file ownership, exact bytes and hash, including zero-byte streams, without changing the nonempty shared JSON-reference contract. Raw streams and acquisition are never re-embedded in the index. Each archival attempt namespaces all leaves and its final index by the exact archive-authorization digest. A pre-rename failure preserves its partial evidence and original lock; a separately issued fresh authorization can recheck and archive independently, without overwriting prior bytes or automatically retrying the same approval. The exclusive `control-archive.lock` fences other acquisition throughout archival; authority, STOP, admitted state/evidence and marker absence are rechecked across awaits and before writes. Exact authorization, all referenced leaves and the index are read back and file/directory-fsynced before renaming only the admitted control lock into its retained archive. Every source/state/native/history/STOP byte is preserved. It never infers staleness from age, automatically retries, renews authority or deletes evidence. Legacy malformed/unbound ownership, a live/reused PID or an incomplete/changed archival fence requires separately reviewed reconciliation. A storage failure after lock rename retains that fence. A completed journal needs lock archival only, not replay of transition phases.

The new launcher is `node scripts/rollout/standing-launcher.mjs /absolute/private/control`. `readActiveGeneration(controlDirectory)` returns validated pointer/config/approval/plan; `runActiveGeneration(controlDirectory)` binds its executing module root/bytes to the approved automation, holds the shared control lease through one poll and writes bounded independent `launcher-status.json` start/end/exit information even when dispatcher state cannot be read. The imported dispatcher independently checks its own executing root before polling. A separate approved checkout cannot authorize a stale executing copy. Installation, switching the live launcher, removal of STOP and resumed deployment each require their own operational receipt; this implementation installs or resumes nothing.

Immutable config contains `generationControl:{controlDirectory,generationId,epochId}`. The validated launcher supplies runtime `generationFence:{controlDirectory,pointerSha256}`. The pointer digest is never embedded in its own config, avoiding a pointer/config hash cycle. `generationDigest` identifies each exact service code/runtime/PATH context; `operationalGenerationDigest` binds the dispatcher and both named contexts. Configuration/approval/candidate identities remain separately pinned. `assertGenerationFence(value, adapterConfig?)` rechecks pointer, journal, epoch, code and configuration before applicable writes; `assertGenerationExecution` adds current STOP/policy, continuation/native expiry, exact attempt and fresh naeil prerequisites before new actions. Adapters recheck direct rollback/recovery paths independently. Fence loss retains uncertainty and locks; STOP does not prevent completion evidence for an already admitted bounded native transaction.

Expired current-generation native success uses a fresh verification ID with `reverification` lineage to immutable evidence of its exact successful native request/result and artifact. `assertGenerationVerification` requires that lineage, the current epoch and the exact durable invoking verification intent/barrier; it preserves current source/adoption, expiry and fresh naeil checks. Completed verification IDs cannot be reused. Both native adapters independently reject verifier envelopes, including a read-only flag without lineage. Read-only verification never authorizes another native attempt. The original successful request/result and every appended verification remain retained.

Historical naeil receipts without `expectationsSha256` remain historical. Before Estimate starts, the dispatcher obtains a fresh current-generation verification of the original or separately approved exact site target, with current routes/reference/expectation digest. It stores a bounded immutable current-epoch `naeilPrerequisite` reference that each native execution boundary independently validates. Expired, changed or failed site verification prevents native progress. Observer/verifier/session/render work uses the same fence; optional `beforeAction` callbacks reach nested menu/account focus, key, click and mouse actions, while `beforeWrite` guards persistence. An admitted session refresh can persist its rotated result while STOP blocks subsequent session/browser actions. Fence loss preserves unresolved refresh evidence. See [site continuation and standalone validation](site-continuation.md) for the separate exact approval channel and Task8 input/session/evidence contract. Transition keeps the original naeil predecessor and exact native predecessors while validating an approved current-site observation through that channel.

`releaseIdentityDigest(release)` excludes only `.path` from the known `archive`, `siteArchive`, `contract`, `account` and `expectations` assets. It retains every other public field, optional asset, URL, metadata and digest. Moving local materialized bytes between epochs is equivalent; changing published identity is not. Site continuation uses this helper and the same operational fence without modifying frozen release records. The separate STOP-safe standalone entrypoint has its own exact read-only approval and never supplies native execution authority, including through a nested current-epoch prerequisite envelope. Independent native admission requires that nested request's exact operational control/pointer/config/service/target and trust bindings. Standalone validation uses the existing authorized canonical session cache in place with its shared refresh lock and exact cache/marker/atomic-temporary write hooks; evidence stays in a separate workspace, with no second rotating cache or general external-directory write grant.

## Private verification and evidence

Protected checks use an existing authorized account through a private renewing Supabase session. Rotation persists atomically before browser use, and the refreshed session must outlive the entire configured verification deadline plus five minutes. Revocation, expiry, another user, overlapping refresh or an ambiguous refresh outcome stops verification; it never falls back to anonymous success. Public routes use independent anonymous contexts. Sessions, action configs, backups and raw native logs stay owner-only outside the repositories.

Verification binds identity before/after, exact routes and structural markers, frozen geometry/colors, canonical links, menu/theme/focus behavior and account styles. It does not collect account names, email, business content or browser traces, click logout, call a model, or change central grants. The production standing verifier disables screenshots; isolated tests exercise destructive and dirty-state flows.

A complete receipt names the three selected services and exact release/source/artifact/reference identities. Installation and successful baseline adoption are distinct from a later genuine-release end-to-end observation. Do not invent a patch to demonstrate success or describe a future release as tested before it exists.

## Publishing the next patch release

Preserve the frozen0.7.1 archive, references, tag and assets. For the next genuine fix patch, follow this order:

1. Commit the package source on main and wait for a successful **push** run of `.github/workflows/verify.yml` for that exact SHA. Freeze the npm archive from that clean source.
2. Select the exact site source SHA on main; require its successful push verification run and its Git/Vercel production deployment. Pack the separate site archive from that clean SHA and compare its public runtime with the frozen npm archive.
3. Generate chrome and account references from the frozen package's reviewed source/archive using the [maintained capture commands](release-preparation.md). Run `node scripts/rollout/prepare-release.mjs prepare INPUT.json` to validate provenance fields, runtime parity and reference metadata, and assemble a fresh private asset directory.
4. Create a **draft** release with every prepared asset, including `release.json` and `site-runtime-verification.json`. Export its actual asset listing and run `node scripts/rollout/prepare-release.mjs check OUTPUT_DIRECTORY DRAFT_ASSETS.json`. Publish only after that check and the separate npm byte-identity/registry-consumption checks pass.

Never add, replace or delete assets, or move the tag, after publication: the worker blocks with `published-release-changed`. GitHub platform immutable releases is currently false; worker-side immutability checks still apply. Keep other main merges outside the release window until the observer verifies the selected site SHA. If an unapproved revision is live, the observer defers with `site-revision-not-approved`. Main pushes no longer cancel each other's CI; a cancelled exact-SHA run is treated as waiting and can be re-run. Local preparation does not prove main ancestry, successful CI, clean-source packing or a live deployment.

## Monitoring

After **every** dispatcher poll, including a nonzero exit, the private launcher should run `node scripts/rollout/standing-monitor.mjs CONFIG --dispatcher-exit N`. Installing this hook in the live launcher is a separate reviewed operation. The monitor reads private `summary.json` and `state.json`, writes current `alerts.json`, and persists first-seen timers, notification history, cleared alerts and delivery failures in `monitor.json` (0600). `monitor-notification.json` contains the notifications selected for the current delivery attempt.

Blocked state, nonzero dispatcher exit, missing state/summary or observations older than20minutes alert immediately. Waiting/deferred states alert after6hours; authorization warns within14days and alerts on expiry; STOP warns after24hours. Stable fingerprints notify on first observation, escalation and at most once per24hours while present. Optional `config.monitor` settings are `staleSeconds`, `waitingSeconds`, `expiryWarningSeconds`, `stopWarningSeconds` and `repeatSeconds`, subject to the bounds in [standing-monitor.mjs](../../scripts/rollout/standing-monitor.mjs).

Delivery to a person requires an explicitly configured `monitor.notifier` (`file`, `args`, `timeoutMs`): an absolute executable pinned in `trustedFiles`, invoked without a shell with the private payload path in `NAEIL_STANDING_ALERT_FILE`. Script arguments must also be pinned. Child output is never copied into alerts; notifier failure is recorded without crashing the monitor. With no notifier, new notifications produce bounded stderr lines. **No external notifier or recipient is configured yet.**

## Operator checks

The private configuration records the immutable automation checkout, complete trusted executable/helper hashes, explicit execution PATH, existing account session, service configs and bounded policy. Native consumers remain on dedicated `rollout/standing` branches; changes since each reviewed source may include only the exact UI dependency, lockfile and vendored package. The updater rejects package metadata changes outside `dependencies["@naeil/ui"]` and lockfile changes outside the UI importer/package/snapshot blocks before committing; any other dependency graph change requires review. Recompute pins only after reviewing the changed code, never as automatic recovery from a mismatch.

Dependency-update commits made by the worker on each consumer’s local `rollout/standing` branch are not pushed automatically. Include those clones (or a git bundle of `rollout/standing`) in the recovery inventory before replacing a host.

With the configured Node executable, `scripts/rollout/standing-dispatcher.mjs plan /absolute/private/config.json` validates configuration without dispatch. `poll` performs one bounded pass. The local `dev.naeil.ui-standing-rollout` LaunchAgent supplies a five-minute cadence and obtains the existing GitHub credential in memory through a fixed local launcher. Child transport forwards `GH_TOKEN`, `GITHUB_TOKEN` and `NAEIL_STANDING_VERCEL_TOKEN` only to the naeil observer rollout invocation, never to verifiers, native adapters or native bridges.

Create the configured `policy.stopFile` to block new stages. `standing-dispatcher.mjs inspect CONFIG` reads the blocked record, each service's bound result, the retained `output.json`, Estimate lock/marker/ledger presence and the live public identities without changing anything. `standing-dispatcher.mjs reconcile CONFIG RELEASE_ID SERVICE_ID RESOLUTION --approved-by NAME --reason TEXT` accepts only `retry-pre-mutation` (a bound result proves `mutationAttempted=false`) and `retry-after-gate-failure` (a bound gate failure proves the runtime was untouched, the Estimate lock and marker are absent and the live identity equals the previously verified artifact). It appends the prior record, approver and reason to the release history and lets the next poll start a new attempt. Uncertain or runtime-changing native work is never reconciled this way: preserve the marker and current data, determine which stage completed and use the native recovery procedure. Do not delete a marker to induce a replay. An expired authorization window requires a new reviewed policy before further patches run.
