## App-owned adapter contract

Each service's reviewed `deployment.adapterId` selects one entry in `adapters.json`. Unknown integrations block visibly. A service that has not adopted the package can use an authorized migration adapter; absent that adapter it remains `not-adopted`. The coordinator does not guess deployment platforms, stop unrelated processes, inspect business data or run invented platform success commands.

The Estimate update command uses `update-consumer.mjs`: frozen release/policy checks, an explicitly provisioned clean `rollout/` bot worktree, exact versioned vendor replacement, pinned pnpm install plus frozen install, archive/lock/installed-version validation, restricted changed paths and a local bot commit. The first install explicitly updates the lock even under CI, then a separate frozen install verifies it. Manifest/lock/vendor targets cannot be symlinks or escaping paths. Real pinned pnpm against fictional archives and tracked symlink regressions passed. A matching installed release is idempotent. It does not push or change an owner checkout. Failures leave the bot checkout for reconciliation, with no reset/replay. Both adapter and `options.update` remain disabled. Naeil consumes the same reviewed package source. Other consumers still need corresponding update/build/platform adapters. Frozen inputs/configuration are required for each common release.

## Disabled Vercel bridge

`vercel-adapter.mjs` uses the existing project's locally reviewed `.vercel/project.json`; its SHA-256 must match `projectContextSha256`. It never runs link/pull or creates a project. Before work it checks the configured CLI's exact version and uses authenticated read-only project metadata to match project/team IDs. Credentials stay in the authorized runner's existing CLI session/environment, never JSON config or command arguments. Raw CLI stdout/stderr and authenticated API objects are not persisted; only whitelisted public deployment provenance is written.

`build` runs `vercel build --prod` against that existing context with the fixed application build identity. It verifies the Next BUILD_ID, compiled identity and the explicitly reviewed identity file inside `.vercel/output`. `package` checks the same clean source and complete output bytes/modes/contained symlinks, rejects credential/environment filenames, copies only `.vercel/output` plus minimal project IDs and public artifact metadata, and creates a SHA-256-addressed tar and directory. The durable artifact store must retain both; this same-runner implementation deploys the verified immutable directory and does not extract arbitrary archives. Changing source, output, identity or project context prevents deployment. The standalone tar helper remains available for local tests but is not the configured Vercel artifact.

The previous-artifact pointer must include the normal immutable artifact fields plus `platform:{kind:"vercel-prebuilt",projectId,teamId,deploymentId,deploymentUrl}`. It must match the previous exact UI version/current contract, resolve to a READY production deployment with matching source/artifact/digest metadata, expose its matching public identity and currently own the inventoried production hostname. Historical GitHub success metadata or the existing 404 identity cannot supply this baseline. Operator review must establish the real compatible previous artifact; the bridge does not fabricate provenance for an older deployment.

`deploy` invokes the documented `vercel deploy --prebuilt --prod --skip-domain --yes`, adding source/artifact/digest metadata. `--skip-domain` prevents automatic production-domain promotion. Before and after it, the configured production alias must still resolve to the previous deployment. Deployment inspection through the documented JSON API validates READY state, production target, exact project/team/source/artifact/digest and immutable URL, followed by that deployment's public identity. `activate` promotes the exact successful deployment ID; `rollback` targets only the verified previous deployment ID using `vercel rollback`. Both verify the production alias and public identity afterward. A changed unrelated alias blocks mutation. Vercel plan-level rollback eligibility and deployment protection/access must be validated on the eventual runner; no bypass or plan change is implemented.

Every platform stage writes an fsynced pre-action marker and holds a project lock. Completed retries revalidate artifacts/platform state without repeating mutations. Failed/interrupted attempts cannot silently replay. Once a mutation was dispatched, timeout or failed postcondition leaves `uncertain` state for explicit platform reconciliation; a pending/uncertain promotion blocks automatic rollback because the accepted promotion may still finish. Stop/approval gates are checked immediately before dispatch. Existing coordinator markers also remain authoritative. The canonical domain's actual browser contract is still checked independently by `verify-ui-production.mjs`; deployment/alias success does not replace it.

Public documentation reads and mocked subprocess execution are the only Vercel-related actions performed by this implementation.

Steps run in order and stop their dependent work on failure:

1. `update` owns the consumer checkout, exact dependency update and lockfile/archive reconciliation. Return `uiVersion`, `archiveSha256`, `dependencyExact:true` and the full updated app `sourceRevision`. If review/merge is pending, return `pending:true` plus `pullRequest`; the state stays `pr-pending` and no build or deployment runs.
2. `test` and `build` run the app's real checks and production build against that exact update. Each returns `passed:true`; nonzero exit or a missing pass fails the gate.
3. `package` returns `artifact` and `previousArtifact`. The new artifact must include `id`, `sha256`, `immutable:true`, `storageRef`, absolute local `path`, app `sourceRevision`, and `ui:{version,contractVersion}`. The coordinator hashes the actual local package bytes and matches them to the receipt. `storageRef` must contain the full digest and refer to immutable storage; for example a digest-addressed container/object/deployment record. It must be an executable/deployable app artifact, not merely a Git diff. The previous artifact needs the same immutable identity fields except local `path`; its digest and ID must differ, and its UI version must match the release's previous version. A missing rollback artifact blocks deployment.
4. `deploy` uploads/releases **those exact bytes** and returns real `deploymentId`, `artifactId` and `artifactSha256`. This is an app/platform integration point, not a claim that upload activated production.
5. `activate` promotes the artifact or restarts the app using the immutable artifact. Return `activated:true`, matching `artifactId` and `artifactSha256`; return `pending:true` if manual/external activation is outstanding. The result remains `activation-pending` until verified.
6. The coordinator reads `/.well-known/naeil-ui.json`, runs the independent real browser verifier for every inventoried canonical UI route, and reads identity again. The release manifest also binds the browser reference’s actual bytes/archive/source/UI/contract before any production request. Expected identity is derived from the packaged app artifact; `service.identity.appId` may name the existing public app identity when it differs from the stable inventory service ID. Redirects, wrong/stale app/source/artifact/UI/contract identity, missing shared header/footer, missing route coverage or browser contract mismatches fail. HTTP 200, expected text and a package import cannot pass this step.

Every canonical route requires `renderState.access` (`public` or `protected`). Protected routes additionally require a reviewed `renderState.visible` selector that belongs to the authenticated screen; optional `hidden` selectors reject a visible login gate. These structural checks do not read element text or protected data. The verifier checks route and state before and after the menu/theme/font/screenshot sequence. Same-URL login/dashboard and locale variants have separate `routeKey` receipts; one result cannot certify the other. Existing production verification is unauthenticated, so a protected marker cannot pass until reviewed safe access exists. Local fixture hooks are restricted to loopback and produce only local evidence. Home's explicit `chrome.themeControlLabels` preserves its KO/EN theme control labels; the verifier still requires mutually exclusive real light/dark classes, canonical catalog and Escape focus restoration.

The public identity contains only `{schemaVersion:1,appId,artifactId,sourceRevision,ui:{version,contractVersion}}`. Internal paths, storage credentials, full manifests and environments remain private. Browser verification is isolated and unauthenticated; protected routes need separately reviewed fixtures/verification capability and stay unresolved rather than counting a login redirect as their result.

## Idempotency, stop and rollback

The app runner owns a **durable** `stateDirectory`, not a temporary CI checkout. Receipts are stored under `RELEASE_ID/SERVICE_ID/receipt.json`; an exclusive lock prevents two coordinator instances using that directory concurrently. Each step is persisted before invocation. A crash/interruption or completed failure cannot silently retry mutations. Same-input reruns return a fresh existing receipt; changed release identity, routes, adapter, policy or expired evidence fail as stale. The adapter must independently persist/enforce `idempotencyKey=RELEASE_ID:SERVICE_ID` at the app/platform boundary to cover a process death after a side effect but before a receipt. The coordinator lock cannot replace platform idempotency.

Do not delete a failed receipt to obtain a green retry. Diagnose the step, reconcile any platform side effect and record a separately approved retry/state-directory decision while retaining the original receipt. Stale production evidence requires a new reviewed verification/run decision; rerunning the CLI does not refresh its timestamp automatically.

Create the configured stop file on each authorized runner to stop the next dependent action. The stop switch blocks rollback too; operations must explicitly decide what may run after stopping. Repository disablement prevents new workflow service jobs but does not retroactively interrupt an already running external command. Commands have explicit timeouts; interruption of a remote platform operation may require app-owned reconciliation.

When activation/production verification fails, automatic code rollback runs **only** if the same recorded policy explicitly has `rollbackApproved:true` and `rollbackScope:"code-only"`, and the stop switch is clear. The rollback adapter receives only the recorded previous immutable app artifact as its target and must return its matching ID/digest plus `activated:true`. The failed release remains failed; the coordinator independently reads the previous artifact's exact production identity before recording `previous-identity-verified`. Its browser status stays unverified, and that rollback can never count as success for the failed release. Rollback errors remain recorded. There is no database, environment, account, family/business-data or infrastructure rollback in this contract. App adapters must not smuggle such changes into code rollback.

## Commands and aggregation

After frozen inputs and approvals actually exist:

```sh
# Read-only policy/runner plan; requires a valid frozen release manifest.
node scripts/rollout/rollout.mjs plan docs/rollout /tmp/naeil-rollout-state

# Frozen public downloads only; no app execution.
node scripts/rollout/workflow.mjs materialize docs/rollout /tmp/naeil-rollout-state

# Authorized app-owned runner execution; uses adapter.stateDirectory durably.
node scripts/rollout/workflow.mjs run-service docs/rollout /tmp/naeil-rollout-evidence APP_ID

# All inventoried services/routes/states and DNS scope participate, not only dispatched apps.
node scripts/rollout/workflow.mjs aggregate docs/rollout /tmp/naeil-rollout-evidence

# Exact post-deploy identity AND actual browser contract check; old optional-text API removed.
./scripts/verify-deploy.sh --origin https://example.com --expected expected-identity.json --routes routes.json --release release.json --reference frozen-reference.json --output test-results/production
```

The guarded workflow computes an explicit per-app runner matrix from reviewed config, dispatches the same pipeline and collects receipts even when a service job fails. It serializes entire app pipelines with `max-parallel:1` and uses matrix `fail-fast:true`: failure cancels pending service jobs before further consumers can activate. This conservative first implementation does not run consumer builds concurrently. Global workflow concurrency prevents overlapping runs. Local stop files do not constitute a distributed stop signal; app-owned commands already accepted by a platform require reconciliation if interrupted. A failed/interrupted receipt prevents an automatic same-state retry, and an additional execution decision must be reviewed. Its aggregate runs after failed/skipped/cancelled service jobs; it does not convert missing jobs to successes. Receipt fingerprints exclude runner-local frozen-input paths, permitting independent runner aggregation while retaining the immutable bytes/reference identities.

States include `review-required`, `pr-pending`, `gate-failed`, `not-deployed`, `activation-pending`, `production-verified`, `approved-exception`, `unresolved` and `not-adopted`. Only `production-verified` and a recorded `approved-exception` can close a service. A service exception needs exact `serviceId`, `releaseId`, identified `approvedBy`, `approvalRef`, `reason` and future `expiresAt`. An incomplete DNS inventory needs its own approval with `scope:"dns-inventory"`; a service exception does not close DNS. Exceptions remain visible in the aggregate. Non-UI routes remain visible exclusions; named canonical routes may be skipped only by a recorded release/service/path/routeKey approval with the same approval fields and expiry. A routeKey binds the exact path, expected destination, locale, state, render-state markers and chrome adapter; another state or locale is not covered. Route exceptions cannot close an entire service. Third-party-access, unavailable-UI and showcase routes require recorded exceptions. A service with no remaining canonical UI routes cannot claim production verification; it needs an explicit service exception. Missing routes, stale receipts, changed release/service inventories and unknown services cannot silently produce `complete:true`.
