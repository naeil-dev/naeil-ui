# 인증 운영 전환 독립 방향 검토 — 2026-10-20

**A2의 추가 설계·구현을 멈추고, 현재 호스팅을 우선하는 방향으로 돌아가는 것이 두 리뷰의 공통 권고다.** 이번 메인은 허용된 설계 검토 범위에서 작업했고 실제 운영을 바꾸지 않았다. 판단의 문제는 첫 검토에서 “채택 보류” 결론을 낸 뒤에도, 기존 인증 계약을 유지하려고 새 서버·TLS 전달 프로세스·인증서 운영을 계속 구체화한 데 있다. 실제 Jay의 새 인증 연결은 여전히 미완료다.

이 보고서는 사용자가 요청한 방향 리뷰의 결과다. 보안 정책 변경, 새로운 구현, 배포·계정·프로세스 적용을 승인하지 않는다. 사용자가 중단시킨 A2 작업을 이 리뷰로 재개하지 않는다.

**방향이 어긋난 지점**

첫 A2 검토에는 이유와 허용이 있었다. 원 인계가 현재 조건을 충족하는 수단이 없으면 구조 결정을 제시하도록 했고, 사용자는 전체 HTTPS 진입점 변경을 설명받은 뒤 별도 설계 검토를 허용했다. 이를 무단 실행이나 같은 승인의 반복으로 설명하지 않는다. 이번 메인은 완료된 기능 테스트를 반복하지도 않았다. [대화의 첫 허용](evidence/auth-direction-independent-review-2026-10-20/visible-conversation.md:74).

실질적인 판단 문제는 **“채택 보류” 이후**다. 첫 검토로 사이트뿐 아니라 Estimate 전체 수신 구조, Home의 연결 처리, Vercel 지원 조건까지 영향을 받는다는 사실이 드러났다. 사용자가 “너가 지금 해야한다고 판단되면 진행해줘”라고 판단을 맡겼을 때, 메인은 이 투자가 필요한지 재평가하는 대신 구체화를 필요한 후속 작업으로 선택했다. [당시 질문과 답변](evidence/auth-direction-independent-review-2026-10-20/visible-conversation.md:166).

인증 시도·취소 처리 보존 → relay → 원문 query/Host 보존 → Next 내부 metadata 고정 → 소유 TLS 진입점 → 둘째 구간 통제 → 전체 서비스의 인증서·로그·복구 운영으로 범위가 커졌다. 각 기술 선택에는 이유가 있지만, 그 선택을 모두 고정한 채 주변 환경을 바꾸는 것이 사용자 목표에 가장 적합한지는 별도 판단이다. 현재 API가 Next16.1.7과 실제 own initURL을 요구하는 것은 확인되는 구현 계약이며, Home에서 접근권을 관리한다는 목적 그 자체는 아니다. [현재 API](../../src/pages/api/internal/service-return.ts:25), [relay 선택 이유](../superpowers/specs/2026-10-18-exact-callback-return-design.md:7).

하위 검토는 Next·로그·채널의 일관성을 확인했다. 그 결과가 A2의 투자 필요성까지 증명하지는 않는다. “설계 완료”, “최소 후보”, VM 기본요금과 보존 검사 통과를 앞세운 보고도 전체 운영 부담과 인증 미완료 상태를 충분히 전달하지 못했다. 기존 기록에는 제약이 적혀 있었지만, 판단을 맡긴 사용자에게 우선해서 제시해야 할 내용이었다.

남는 평가 차이는 **플랫폼 보존 가능성의 잔여 위험을 얼마나 낮게 볼지**다. Opus는 PKCE를 근거로 수용을 권할 만하다고 본다. Astra는 nonce·오류 query와 실제 보존 범위까지 안전하다고 결론 내릴 근거가 부족하다고 본다. 메인은 후자의 근거 한계를 따른다. 실제 보존 여부·기간을 확인하지 않은 채 “잠깐 남을 뿐” 또는 “안전하다”고 표현하지 않는다.

PKCE는 verifier가 없는 공격자의 code 교환을 막는 중요한 방어다. 이것은 이 프로젝트의 플랫폼 로그 보존 기간이나 로그 허용 정책을 인증하는 근거와 다르다. OAuth 보안 표준도 PKCE와 누출 방지 조치를 구분한다. [RFC9700 §4.2.4](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.2.4), [RFC7636 §1](https://www.rfc-editor.org/rfc/rfc7636.html#section-1).

**권고 방향과 가장 작은 결정**

권고는 **현재 호스팅을 우선하고, 로그인 후 각 서비스로 돌아오는 callback·로그 보증 계약을 필요한 범위에서 명시적으로 재설계하는 방향**이다. A2의 서버·sidecar 상세 설계나 구현은 계속하지 않는다. 기존 코드·테스트·관측·영수증은 보존하고 재사용한다.

| --- | --- | --- |
| 현재 호스팅과 현재 OP01–03 모두 유지 | 지금 계약을 변경하지 않음 | 현재 근거에는 완성된 적용 경로가 없다. 새 인증 활성화를 보류한다. 플랫폼 전체 불가능으로 단정하지 않는다 |

그 선택 다음의 최소 작업 단위는 **현재 호스팅에서 동작할 하나의 callback 변경안**이다. 바뀌는 규칙·유지하는 보호·OP02/03 충족 근거·유한한 검증·남는 적용 승인을 함께 고정해야 한다. 전체 인프라 설계, 새 observer, 이전 suite 반복이나 우선 Production 배포가 아니다. 이 보고서가 현재 방향 결정 자료이며 같은 내용의 준비 문서를 다시 연속 생산하지 않는다.

**메인의 설명 정정**

설계 검토와 구체화에는 허용이 있었다. 운영·계정·코드는 바꾸지 않았다. 그럼에도 진행할지 판단을 맡긴 시점에 멈출 근거를 충분히 사용하지 못한 것은 메인의 판단 문제다. “콜백 인증정보가 유출됐다”는 사실도 없다. 정확한 관측은 무해한 health query의 저장이며 실제 callback의 비저장은 미입증이다. 이번 메인이 새로 사용 가능하게 만든 인증 기능은 없었다.

따라서 최근 사과는 “허용 없이 실행했다”는 뜻으로 확대하지 않고, **필요성 판단보다 상세 설계의 완성을 앞세웠다**는 문제로 정확히 정정한다. 기존 보안 조건을 모두 자의적인 규칙으로 치부하거나, 반대로 사업 목적과 동일한 불변 조건으로 취급하지 않는다.
