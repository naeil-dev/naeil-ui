# 인증 운영 전환 방향 검토와 실행 계획 제안 — 2026-10-19

**검토·계획 제안 완료. 새 구현·설계 변경·운영 적용 승인이 아니다.**

원래 목표는 현재 호스팅과 기존 계정을 유지하면서 **Jay가 먼저 Estimate에 개인 계정으로 로그인하고, Home에서 접근권을 관리하게 하는 것**이다. 이후 Jev와 새 회원 초대를 연결한다. 큰 목표와 이 순서는 맞다. 다만 다음 작업을 새 관측기 제작으로 고정하고 원인 추적이 다른 운영 준비를 기다리게 하는 방식은 바꿔야 한다.

권고는 **추가 진단을 보류하고, 현재 보안 조건을 충족하는 전달 방법과 실제 전환·복구 절차를 병행해 완성하는 것**이다. 지원되는 해결 수단이 확인되지 않은 부분은 구체적인 결정 사항으로 올린다. 설정할 수 없는 보장을 이미 확보한 것처럼 쓰거나, 원인 이름만 더 알아내는 실험을 자동으로 이어가지 않는다.

상호 검토에서 다음 주장을 바로잡았으며 **최종 권고에는 포함하지 않는다.**

- 로그 허용 또는 query glob 직접 callback을 현 제약 안의 해결책으로 제시하는 것. 이는 별도 정책·구조 변경이며, 서비스 쪽 로그·query·Host·finalizer 문제까지 없애지 않는다. 기존 callback에서 실제 인증정보가 기록됐다는 관측도 없다.
- 변형된 입력을 parser가 거부하기만 하면 원문·alias 요구가 충족된다는 것, 또는 own-initURL을 유지하며 변형을 고칠 수단이 전혀 없다는 것. 두 주장 모두 성립하지 않는다.
- Owner 표시·MFA·임의 SELECT 성공만으로 독립 DB 복구가 확인됐다는 것.
- 과거 정상 종료를 근거로 현재 강제 종료 위험을 허용하거나 사용자에게 금지 조건의 재해석을 맡기는 것.
- 리뷰 횟수를 고정해 새 중요한 결함이 있어도 검토를 끝내는 것.

두 모델은 수정 후 위 경계와 아래 계획의 실질적인 순서에 동의했다. 과거 조사에 얼마만큼의 가치가 있었는지에 대한 평가 차이는 남지만, 현재 다음 행동에는 영향을 주지 않는다.

## 추가 진단을 재개할 조건

한 지점·10건 관측안은 **보존하되 현재 보류**한다. 구현·배포·키·검사 승인도 새로 생기지 않았다. 다음 조건을 모두 갖출 때만 다시 제안한다.

1. 특정 수정 후보 중 무엇을 선택할지 명확하다.
2. 각 가능한 관측이 그 선택을 실제로 바꾼다.
3. 기존 증거로 답할 수 없는 질문이며, 새 wrapper/packaging이 관측 대상에 미치는 영향을 구분한다.
4. 정확한 로컬 범위와 후속 hosted 적용·키 회수 범위, 끝 조건을 완성한다.

| 관측 | 가능한 다음 판단 | 닫을 수 없는 조건 |
| --- | --- | --- |
| entry는 원문, own은 변형 | own 정책을 유지하는 entry 이후 구간 수정 가능성 검토 | OP01/02·raw Host·실제 제품 수용 |
| entry부터 변형, own도 같은 변형 | API parser가 소실된 byte를 복구한다는 접근 중단. entry 이전 지원 수단 검토 | middleware/CDN 단독 원인 확정 |
| entry와 own에서 각각 변형 | 단일 구간 수정 가정 중단 | 우연히 최종 값이 같아진 것을 보존 성공으로 판정 |
| 세 query 모두 원문과 같음 | 새 후보와 이전 후보 차이를 대조 | 과거 문제 종결·비결정성 단정 |
| unknown/unavailable 또는 guard 거부 | 관측 부족으로 종료하고 결정 사항 보고 | 허용표 확대·자동 재시도·다음 observer 자동 추가 |

기존 D01 대조+D03/D09/D12/D30의 H1/H2 총10건을 넘는 확장을 자동 후속으로 삼지 않는다. 추가 범위에는 새로운 결정 이유가 필요하다. parser 영향 분석도 특정 미해결 판정이 수정 선택을 바꿀 때만 좁게 검토하며, fail-closed를 원문 보존 증거로 대체하지 않는다.

## 진행 방식과 완료 기준

- 상태 보고는 **실제로 바뀐 운영 상태 / 남은 차단 조건 / 다음 산출물 / 사용자에게 필요한 결정**으로 간단히 쓴다. 문서 검토·로컬 검증·합성 hosted 관측·실계정 수용을 분리한다.
- 이미 승인된 준비·읽기 전용 확인에는 반복 승인을 요구하지 않는다. 새 적용은 대상·변경·artifact·보존·복구·중단 조건을 완성한 뒤 해당 적용만 요청한다. 승인 미요청/승인됨/소비됨을 구분한다.
- 테스트와 리뷰는 변경과 중요한 미해결 사항에 맞춘다. baseline178이나 전체 suite를 이유 없이 반복하지 않는다. 중요한 새 결함은 해당 범위의 수정·재검토로 해결한다.
- 중앙 정책 적용 후 password-only rollback은 금지한다. 참조 앱과 진행 중 시도가 없어질 때까지 relay를 유지한다.
- Home2455 주소와 현재 호스팅, Google·기존 UUID·Jay 단일 초기 관리자, 회원별 명시 허용표를 유지한다. 자동 SSO·전역 logout·언어 동기화·견적 번역은 추가하지 않는다.
- 새 초대 SMTP 준비는 기존 Jay 전환 준비의 선행조건이 아니다. Supabase 기본 메일 설정과 Home 후보의 새 통합 초대는 별개다. 기존 발송 경로는 미확인이고 직접 SMTP나 relay를 자동 교체하지 않는다.
- **첫 운영 수용은 Jay→Estimate의 승인된 실계정·artifact·HTTPS 검증이다.** 전체 목표 완료에는 이어지는 Jev·새 초대/실메일과 사이트/Jev ko/ja/en·Estimate ja, 로그인·401/403/503·회수·장애 logout·계정 전환·저장 보호·재시작 확인도 필요하다.

이번 작업은 두 모델 검토·쟁점 조정·계획 작성이다. 기존 인증 구현, 운영 설정, 계정·권한·메일·배포·프로세스·fixture는 변경하지 않았다. 과거 증거를 대체하지 않으며, [인계](auth-main-handoff-2026-10-19.md)와 STATUS에는 이 제안의 최신 연결만 추가한다.
