# Local rollout runner

The 0.7.2 acceptance completed on 2026-10-28 (naeil and Estimate verified only, Jev deployed once). Retiring the old launcher needs separate owner confirmation; this page does not activate or retire it. See [the owner-approved design](../superpowers/specs/2026-10-28-local-rollout-runner.md).

The runner handles one pinned 0.7.x release on the owner Mac. Its private config names a new release state directory, a machine-wide lock, STOP, the approval file, and a final plan. The plan lists naeil, Estimate, Jev in order, each with `verify-only` or `deploy`. Completed imported services stay `verify-only`. Consumer build/test/E2E candidates and their exact source, lockfile, archive, tool and artifact bytes are checked independently of runner version.

Preparation produces an immutable final plan with each deployment's candidate, previous artifact and consumer-input digest. Write a draft config whose deploy services name `currentArtifact` and a passed isolated `consumer.candidate`, then run `node scripts/rollout/local-cli.mjs prepare-plan DRAFT_CONFIG CONFIG`. It checks the release assets, candidate proof and recorded predecessor bytes and writes only the new CONFIG (never over an existing file); it creates no state or approval. A missing `candidateBinding` is filled from the candidate's own proof, so review the final plan's source, tool, previous and candidate bindings before granting its single approval. `prepare CONFIG` then re-inspects the live predecessor. Generate the approval template with `node scripts/rollout/local-cli.mjs approval-template CONFIG`. Install that exact template as the approval file only after the owner approves the concrete release plan. It has no expiry. Keep the owner decision in the work record; no second approval chain is needed. STOP or removing the file prevents the next forward stage.

Commands accept a private config path:

```sh
node scripts/rollout/local-cli.mjs prepare-plan DRAFT_CONFIG CONFIG
node scripts/rollout/local-cli.mjs prepare CONFIG
node scripts/rollout/local-cli.mjs verify CONFIG naeil
node scripts/rollout/local-cli.mjs verify CONFIG estimate
node scripts/rollout/local-cli.mjs run CONFIG
node scripts/rollout/local-cli.mjs verify CONFIG jev --recover-verification
node scripts/rollout/local-cli.mjs status CONFIG
node scripts/rollout/local-cli.mjs rollback CONFIG TRANSACTION_ID
```

`prepare` and `verify` need no deployment approval; they still respect STOP. `verify` reports a deploy-mode service without a completed deployment as `unverified` (exit 1) and does not hold the later approved run. `status` takes no lock and writes nothing; it also shows whether the machine lock exists. `run` cannot select a later service and skip its predecessors. Production verification covers public and authenticated routes, account menus and frozen render expectations. Credentials remain inside the verifier child; output contains only bounded diagnostic fields and receipts.

Network/403/rate-limit failures retry with bounded backoff (default 3 attempts, 250ms then 500ms) and then stop as `retryable`; a long challenge needs an explicit rerun, not an automatic watcher. Identity, digest and UI mismatches remain `held`; explicitly recheck corrected inputs with `--retry-held`. Authentication requiring renewal is reported separately. An uncertain session refresh latches `manual-recovery`. After the owner resolves the session (including any retained `.refresh-lock`), `verify CONFIG SERVICE --recover-verification` re-verifies only that service; it records an immutable receipt referencing the original failure and grants no deploy or native authority. A remaining refresh lock fails again. The same flag resumes a verification whose child outlived its stage once the machine lock is free. STOP before the refresh request leaves no lock; a rotated session is saved before its lifetime is judged. A native call with no conclusive result becomes `manual-recovery`; it is never automatically repeated. Known failed activation with proven recovery retains its original failure receipt.

Rollback ignores STOP and release approval, using only the transaction's recorded predecessor and retained native helper. A completed deployment can be rolled back while its candidate is unhealthy (5xx, wrong served identity, or a crash that left no owned process). Code, journal, ownership, idle/lease and data checks still apply: a busy lease or connection defers, and Estimate refuses while its application lock file or an unlistening owned process remains. The restored predecessor must pass health; if it is unhealthy too, the outcome needs manual recovery. Native helpers and verifier children start only after their process group is durably registered in the machine lock. Transactions retained by the adfc995 Jev helper (the 0.7.2 acceptance) recover through the reviewed helper pinned in `local-consumers.mjs` after the retained bytes verify; this applies only when the rollback is run with this runner version. Rollback and status load no browser verifier or `node_modules`. Actual production rollback has not been exercised; the evidence is synthetic. Unknown or surviving workers retain the machine lock. `recover-lock CONFIG OWNER_ID` refuses a live owner, child or process group; use it only after reviewing the recorded uncertainty and with any required owner authorization for operational lock changes, then explicitly request the transaction rollback. Do not erase locks or edit state to force a retry.

For the 0.7.2 acceptance, preserve all original epochs, archives and failures. Exclude the old writer with its compatible control lock and check worker absence before final import/acceptance. The release approval includes that concrete exclusion. After all three services are production-verified, obtain the separate owner confirmation to disable/bootout the old launcher and retire its source paths. No naeil/Estimate redeployment, consumer push, package publication or PR merge is part of this acceptance.

The acceptance plan's `handoff` pins the original STOP, stable control pointer/journal/config references, and exact old automation/consumer worker directories. Old poll timestamps do not enter the approval digest. `run` acquires the compatible old control lock, checks workers, then imports exact service facts and records the old state digest in the new directory. It retains that exclusion lock on success or failure until retirement. Worker inspection uses executable/cwd metadata, never process arguments or environment contents. The lock protocol covers the configured launcher path; independently relocated uncooperative workers cannot be identified by directory metadata alone.

The new runner has its own STOP path. Keep the original STOP while acceptance runs; create the new STOP or remove the new approval to cancel forward work. Explicit rollback bypasses the acceptance wrapper and uses the retained transaction. After an interrupted deploy or rollback and explicit dead-worker lock recovery, exact predecessor identity completes reconciliation without stopping the service; exact candidate identity permits only the same transaction rollback using a fresh journal-bound inspection receipt. Mixed identity or a live worker remains manual recovery. Safe rollback deferrals can be retried explicitly; each native retry preserves earlier journals and backup attempts.
